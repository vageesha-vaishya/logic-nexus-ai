# Workstream 5: Non-LLM AI workloads and observability

## Scope covered

- `services/timesfm-service/` (`app.py`, `Dockerfile`) read in full; its 2 callers (`supabase/functions/forecast-demand/index.ts`, `supabase/functions/container-demand/index.ts`) read in full for how `TIMESFM_URL` is used and what happens when it is absent.

- **Not covered** (per the plan's split): the gateways themselves in depth (`services/llm-gateway`, `_shared/llm-gateway.ts`) — Task 1's surface; edge-function data-flow specifics — Task 2 Step 5; client/browser exposure — Task 3; the shared vLLM rig's reachability — Task 4. Where those surfaces intersect this workstream's cost-visibility question, the intersection is noted but not re-audited.

## Findings

### F-5.1 — The "TimesFM" service is Holt-Winters exponential smoothing, and isn't deployed to production either [Medium]
**What:** `services/timesfm-service/app.py` implements `/forecast` using `statsmodels.tsa.holtwinters.ExponentialSmoothing` — a classical statistical smoothing method, not the TimesFM transformer foundation model the name implies. Separately, it is only wired into the local-dev `docker-compose.yml`; the production edge-functions container has no `TIMESFM_URL` set, and no Coolify app named `timesfm-service` exists. As a result, in production `forecast-demand` (`supabase/functions/forecast-demand/index.ts:112-169`) always takes its `catch` branch and calls `https://api.openai.com/v1/chat/completions` with model `gpt-4o-mini` and a prompt that literally claims to use "a Transformer-based approach" (line 83) — a description that is true of neither code path that can actually run. `container-demand` (`supabase/functions/container-demand/index.ts:57-71`) checks `if (timesfmUrl)`, finds it unset, and silently falls back to a 6-point moving average, logging `model_used: "moving-average"`.
**Evidence:** `services/timesfm-service/app.py:6,36-44` (`ExponentialSmoothing` import and fit call); `docker-compose.yml:114-120` (only compose entry, local ports); `ssh hostinger-vps "docker exec functions-i64jlyerora7ao9vkw5sweh3-151315126444 env | grep -iE 'TIMESFM'"` → no output; Coolify `GET /api/v1/applications` (24 apps enumerated by name) → no `timesfm-service` entry; `supabase/functions/forecast-demand/index.ts:114,147,204`; `supabase/functions/container-demand/index.ts:57-86`.
**Observed or inferred:** Observed (all of the above is direct file/command output). That the OpenAI branch is the one actually taken in production is inferred from `TIMESFM_URL` being absent — not confirmed by tracing a live request.
**Impact:** The forecast-demand path silently and permanently uses paid OpenAI calls per invocation, with a prompt whose own description of its method is inaccurate; container-demand silently downgrades to a naive heuristic with no LLM or real forecasting model at all. Neither behavior is visible to an operator without reading the source — `model_used` in the audit trail (`"gpt-4o-mini"` / `"moving-average"`) is the only externally visible signal, and see F-5.4 for how rarely that trail is actually written.

### F-5.2 — markets-worker's cost-tracking table is real and well-built, but has recorded nothing for 2+ months [Medium]
**What:** `platform.llm_usage` (written exclusively by `llm_gateway.py`'s `_write_usage()`) is a genuinely useful cost ledger: per-call `provider`, `model`, `input_tokens`/`output_tokens`, `cost_usd` (numeric(12,6)), `tenant_id`, `task_id`, monthly-partitioned. It has 1,459 total rows, but `max(ts) = 2026-06-30 23:47:04+00` — no rows for July, August, or September 2026 as of this audit (2026-09-05). All 5 recorded `task_id`s are `markets.*` (`news_sentiment` 1,356 rows, `daily_brief` 63, `signal_explanation` 36, `research_thread` 3, `portfolio_advisor` 1); total lifetime spend recorded is $0.086959. The `markets-worker` container is confirmed running (`Up 3 days`), but `docker logs --since 48h ... | grep -iE "llm_gateway"` returns zero lines.
**Evidence:** `select min(ts), max(ts), sum(cost_usd) from platform.llm_usage;` → `2026-05-15 08:56:35+00 | 2026-06-30 23:47:04+00 | 0.086959`; `select task_id, count(*), sum(cost_usd) from platform.llm_usage group by task_id;` (5 rows, listed above); `ssh hostinger-vps "docker ps --filter name=biziai4qublf34p3rgiqp22z --format '{{.Status}}'"` → `Up 3 days`; `ssh hostinger-vps "docker logs --since 48h biziai4qublf34p3rgiqp22z-083047027328 2>&1 | grep -iE 'llm_gateway'"` → empty.
**Observed or inferred:** Observed (row data, container status, log grep). The reason for the 2-month silence (feature disabled, scheduled job stopped, or simply no triggering user/tenant activity) is not determined — see Unknowns.
**Impact:** This is the single most complete AI-spend record in the system, and it is stale. Anyone querying it today for "AI spend last month" (August 2026) would get exactly $0 and zero calls — which is indistinguishable, from the query alone, between "we spent nothing" and "this pipeline stopped recording."

### F-5.3 — AI usage/cost data is fragmented across at least 4 disconnected schemas, most of them empty or near-empty [High]
**What:** The brief's table-name regex surfaces AI-usage tables in four separate schemas with no query, view, or reconciliation joining them: `core.llm_invocations` / `core.llm_usage` / `core.llm_provider_configs` — **0 rows in all three**; `gateway.llm_invocations` — **1 row**, `gateway.prompts` — 6, `gateway.prompt_experiments` — 0; `platform.llm_usage` — 1,459 rows but stale since 2026-06-30 (F-5.2), `platform.llm_provider_configs` — 2 rows; `public.ai_audit_logs` — 26 rows total, stale since 2026-05-20 (F-5.4); `public.ai_quote_cache` — 76 rows, stale since 2026-05-20; `public.ai_quote_requests` — 162 rows, last write 2026-08-21 (the only one of these tables with data inside the last month); `markets.ai_briefs` — 1 row; `markets.prompts` — 4 rows.
**Evidence:** `select table_schema, table_name from information_schema.tables where table_name ~ 'llm|ai_|model|prompt|embedding' order by 1,2;` (30 rows, 3 excluded as false positives — see Notes); per-table `select count(*) from ...` for all 15 genuinely AI-related tables (values above); `select min(ts/created_at), max(...)` per table where a timestamp column existed.
**Observed or inferred:** Observed. Cross-reference: Task 1 (W1) independently found `services/llm-gateway` (the codebase that owns the `gateway.*` schema) "not deployed anywhere observed" — consistent with `gateway.llm_invocations` having only 1 row; how that 1 row and `gateway.prompts`' 6 rows got there if the service never ran is not resolved by this workstream (Unknowns).
**Impact:** Even where usage data exists, it is split four ways with different owners, different schemas, different partitioning schemes, and (per the row counts) wildly different levels of actual use. There is no single place to look.

### F-5.4 — Only 2 of 27 edge functions that import the AI-audit helper have ever logged a single AI call [High]
**What:** `grep -rl "_shared/audit" supabase/functions/` matches 28 files (27 importers plus the shared module itself), including `forecast-demand`, `container-demand`, `ingest-email`, `lead-scoring`, `risk-scoring`, `carrier-scoring`, `margin-optimizer`, `route-optimization`, `predict-eta`, `win-probability`, `anomaly-detection`, `revenue-forecasting`, `fleet-utilization`, `smart-reply`, `portal-chatbot`, `nexus-copilot`, `ai-agent`, `ai-message-assistant`, `autonomous-email`, `categorize-document`, `extract-bol-fields`, `ensemble-demand`, `markets-import-holdings`, `markets-portfolios`, `markets-research`, `ai-advisor`, `classify-email`. Querying the table those functions' `logAiCall()` calls write to (`public.ai_audit_logs`) by `function_name` shows exactly 2 distinct values were ever recorded: `classify-email` (18 rows, last 2026-03-12) and `ai-advisor.generate_smart_quotes` (8 rows, last 2026-05-20). Every other importer has zero rows, ever.
**Evidence:** `grep -rl "_shared/audit" supabase/functions/ | wc -l` → 28; `select function_name, count(*), max(created_at) from public.ai_audit_logs group by 1 order by 2 desc;` → exactly the 2 rows above; `supabase/functions/ingest-email/index.ts:181-220` shows the embedding-and-audit step wrapped in a `try { ... } catch (embErr) { logger.warn(...) }` that never surfaces failure to a caller or to any other table — an example of the kind of silent swallow that would explain a "should log but doesn't" gap.
**Observed or inferred:** Observed (the row/function-name data). Whether the 25 silent importers are simply never invoked in production, are invoked but error out before reaching `logAiCall()`, or call `logAudit`/`logAccess` instead of `logAiCall` for their observability needs, is not determined — see Unknowns.
**Impact:** `ai_audit_logs` cannot be treated as a reliable signal of "what AI activity happened" anywhere in this platform — the overwhelming majority of functions built to write to it never have, and the table's last write of any kind is over 3 months before this audit (2026-05-20 vs. 2026-09-05).

### F-5.5 — The one purpose-built "what did we spend on AI" dashboard is hardcoded to fail in production [High]
**What:** `src/features/admin/llm-gateway/useLlmGatewayLists.ts` backs a full admin UI — prompt registry, A/B experiments, a per-call audit list, and a **budget-status view** (`spent_usd`, `limit_usd`, `utilization_pct`, `status: 'ok'|'warning'|'exceeded'`) that is exactly the kind of surface Step 5 asks for. It calls the edge function `llm-admin-list`, which after an admin-role check proxies to `Deno.env.get("LLM_GATEWAY_URL")` and returns HTTP 503 ("gateway not configured") if that variable is unset (`supabase/functions/llm-admin-list/index.ts:85-86`). The live functions container has no `LLM_GATEWAY_URL` set, and there is no standalone "llm-gateway" Coolify application among the 24 live apps — `services/llm-gateway/` (the codebase this dashboard is meant to front) has a `Dockerfile` but is absent from both the local `docker-compose.yml` and every deployed environment observed.
**Evidence:** `supabase/functions/llm-admin-list/index.ts:85-86` (`const gatewayUrl = Deno.env.get("LLM_GATEWAY_URL"); if (!gatewayUrl) return bad("gateway not configured", 503);`); `ssh hostinger-vps "docker exec functions-i64jlyerora7ao9vkw5sweh3-151315126444 env | grep -iE 'LLM_GATEWAY'"` → no output; Coolify `GET /api/v1/applications` → 24 apps, no `llm-gateway`; `grep -n "llm-gateway" docker-compose.yml` → no match.
**Observed or inferred:** Observed. Directly corroborates Task 1 (W1)'s independent finding (F-1.1: "services/llm-gateway... has never run") from the consumer side rather than the service side.
**Impact:** This directly answers Step 5. The only feature in the codebase explicitly designed to show spend-by-prompt/budget-utilization is permanently broken (a config gap, not a bug that could be hit-or-miss) — and even if `LLM_GATEWAY_URL` were set today, the schema it would read from (`gateway.*`) is itself nearly empty (F-5.3), so turning it on would not retroactively produce a usable history.

### F-5.6 — pgvector embedding columns exist on 6 tables in active use, and are 0% populated on all of them [Medium]
**What:** The `vector` extension is installed, and 6 tables carry an `embedding` column: `public.leads` (2,534 rows, 0 with embedding), `sales.leads` (2,534 / 0), `module_crm.module_crm_leads` (2,534 / 0), `public.emails` (33 / 0), `comms.emails` (33 / 0), `public.knowledge_base` (0 rows — table itself is empty). Code that should populate these exists: `supabase/functions/generate-embedding/index.ts` is a manually-invoked (no cron/trigger caller found) batch/single embed endpoint, but only for `knowledge_base` and `master_hts` — it has no code path for `leads` or `emails` at all. `supabase/functions/ingest-email/index.ts:181-220` does attempt to embed `emails.body_text` inline on ingest via OpenAI's `text-embedding-3-small`, but the entire step is wrapped in a `try/catch` that only `logger.warn`s on failure and never blocks or retries. Given 33 real email rows exist with 0% embedded, this step is either failing on every invocation or not being reached for those rows at all.
**Evidence:** `select extname from pg_extension where extname like '%vector%';` → `vector`; `select table_schema, table_name, column_name from information_schema.columns where udt_name='vector';` → the 6 rows above; per-table `select count(*), count(embedding) from ...` (all showed `with_embedding = 0`); `supabase/functions/generate-embedding/index.ts:4` (`type Table = "knowledge_base" | "master_hts"` — no `leads`/`emails` branch exists); `supabase/functions/ingest-email/index.ts:181,218-220`.
**Observed or inferred:** Observed (row counts, code paths). Whether the ingest-email embed step fails on every call vs. the 33 existing rows predate/bypass that code path (e.g. were seeded another way) is not determined from static analysis — see Unknowns.
**Impact:** This is precisely the pattern called out in the audit brief: the schema, the extension, and the write-path code all exist, but the control is not operating — no semantic search or embedding-based retrieval is actually functioning on lead or email data today, regardless of what the table structure implies is possible.

### F-5.7 — Several "AI"-branded scoring functions are hand-tuned linear heuristics with no model or LLM behind them [Informational]
**What:** `supabase/functions/risk-scoring/index.ts:85-90` combines four sub-scores via a fixed weighted sum (`weights = { delay: 0.35, compliance: 0.25, route: 0.2, geopolitical: 0.2 }`) — no trained model, no LLM call. Grepping `lead-scoring`, `win-probability`, `revenue-forecasting`, `anomaly-detection`, `carrier-scoring`, `margin-optimizer`, `predict-eta`, and `fleet-utilization` for any LLM-provider call (`openai.com`, `anthropic.com`, `gemini`, `chat/completions`, `messages.create`) finds none — all are deterministic TypeScript logic. By contrast, `ensemble-demand` and `route-optimization` (same naming convention, same directory structure) do call an LLM provider directly. `services/markets-worker/src/markets_worker/jobs/backtest_engine.py` does genuine numeric work (numpy/polars-based backtesting), a real counter-example of non-LLM, non-trivial quantitative logic in this codebase.
**Evidence:** `supabase/functions/risk-scoring/index.ts:85-90`; `grep -lE "openai\.com|anthropic\.com|gemini|chat/completions|messages\.create" supabase/functions/{revenue-forecasting,win-probability,risk-scoring,lead-scoring,anomaly-detection,carrier-scoring,margin-optimizer,predict-eta,fleet-utilization}/index.ts` → no matches (exit 1); same grep against `ensemble-demand`, `route-optimization` → matched.
**Observed or inferred:** Observed.
**Impact:** No LLM spend or PII exposure risk attaches to these specific functions — useful for scoping sub-project D's cost/governance inventory, since a name-based inventory of "AI features" would otherwise overcount which functions actually carry LLM cost or data-handling risk.

### F-5.8 — The general-purpose (non-AI-specific) mutation-audit table is also effectively unused, unlike the access-decision log [Low]
**What:** `_shared/audit.ts` exports three log functions writing three different tables: `logAiCall()` → `public.ai_audit_logs` (F-5.4), `logAudit()` → `platform.audit_log` (state mutations), `logAccess()` → `platform.access_log` (auth/domain decisions). `platform.audit_log` has 6 rows total, last write 2026-05-22. `platform.access_log` has 9,291 rows, last write 2026-09-01 (4 days before this audit) — clearly active.
**Evidence:** `select count(*), max(ts) from platform.audit_log;` → `6 | 2026-05-22 17:27:28+00`; `select count(*), max(ts) from platform.access_log;` → `9291 | 2026-09-01 06:47:04+00`.
**Observed or inferred:** Observed.
**Impact:** Not an AI-specific finding on its own, but relevant context for Step 4: whether "an action leaves a record" in this codebase depends entirely on which of 3 sibling functions in the same shared module a given caller happens to invoke, and 2 of the 3 are effectively dead despite dozens of importers.

### F-5.9 — Plain answer to Step 5: no, nobody can answer "what did we spend on AI last month, and on what" today [Medium]
**What:** Combining F-5.2, F-5.3, F-5.5, and F-5.8: the most complete cost table (`platform.llm_usage`, real `cost_usd` per call) has recorded nothing for over 2 months; the only other tables with real cost/token fields (`core.llm_usage`, `gateway.llm_invocations`) are empty or have a single row; the legacy AI-audit table (`public.ai_audit_logs`) is written by only 2 of 27 instrumented functions and stopped over 3 months ago; and the one dashboard purpose-built to answer this exact question (`llm-admin-list` / the admin LLM Gateway UI) returns HTTP 503 in production because its backend was never deployed. There is no unified view, materialized or otherwise, across any of these sources.
**Evidence:** See F-5.2, F-5.3, F-5.4, F-5.5 evidence blocks above.
**Impact:** This is the Medium finding this workstream is asked to surface directly for sub-project D. Any AI cost accounting exercise today would have to be done ad hoc, schema-by-schema, and would still miss whatever AI calls (if any) bypass every one of these tables entirely — a possibility this workstream cannot rule out from static analysis alone (see Unknowns).

## Unknowns / not verified

- Why `platform.llm_usage` stopped receiving writes after 2026-06-30 (F-5.2) — whether a scheduled job (e.g. `signal_generator`) was disabled, a scheduler/cron config changed, or there simply has been no tenant activity that triggers those `markets.*` tasks since then. No job-scheduler/cron configuration was located and inspected in this pass.
- Whether the 25 silent `_shared/audit` importers (F-5.4) are never invoked in production, are invoked but error out before reaching `logAiCall()`, or deliberately call `logAudit()`/`logAccess()` instead for their own observability needs — distinguishing these would require function-level invocation/error logs, which were not queried (out of scope for a schema/code read-only pass).
- How `gateway.llm_invocations` (1 row) and `gateway.prompts` (6 rows) came to have any data at all, given Task 1 (W1) independently found `services/llm-gateway` — the only codebase that writes to the `gateway.*` schema — "not deployed anywhere observed." Possibilities include seed/fixture data from a migration, a short-lived manual deployment or test that predates both audits, or a deployment window Task 1 did not observe; not resolved here.
- Whether `ingest-email`'s embedding step (F-5.6) is failing on every invocation (bad model name, quota, API error) versus the 33 existing `emails` rows having been created by some path other than `ingest-email` (e.g. a migration/seed) that never reaches the embed code at all.
- Whether any tenant-facing feature is currently advertised as "semantic search" or relies on the populated state of the `leads`/`emails` vector columns (F-5.6) — this would be a frontend/product-surface question adjacent to W2/W3 and was not chased here.
- Whether `TIMESFM_URL` (or an equivalent forecasting-service URL) is configured in any deployment context beyond the single production functions container checked (e.g., a staging/preview Coolify project not enumerated in the 24-app list retrieved).
- Whether any AI-calling code path in this codebase writes usage data to a destination outside the ~15 tables surfaced by the brief's regex (e.g., an external provider's own dashboard, a log aggregator, or nothing at all) — this audit can only account for what leaves a trace inside this Postgres instance.

## Notes for synthesis

- **Cross-cutting with Task 1 (W1 gateways):** F-5.5 (admin dashboard hardcoded to 503 because `LLM_GATEWAY_URL` is unset) independently corroborates Task 1's F-1.1 (`services/llm-gateway` never deployed) from the consuming side. Between the two workstreams, every angle on `services/llm-gateway` — the service itself, its data schema, and its only UI consumer — points the same direction: built, governed, and completely inert in production.
- **Direct feed for sub-project D (cost visibility):** F-5.9 is the plain "no" this task was asked to produce. The evidence trail (F-5.2, F-5.3, F-5.4, F-5.5) shows this isn't a single missing report — it's four-plus disconnected, mostly-empty-or-stale data sources and one broken dashboard, so remediation is a genuine build effort (pick one schema, wire every AI call path into it, fix the dashboard's backend), not a query someone forgot to write.
- **Schema-drift pattern, consistent with W1's F-1.5:** `core.llm_usage`/`core.llm_invocations`/`core.llm_provider_configs` (all 0 rows) form a third parallel, unused schema family alongside `platform.*` and `gateway.*` — the same "migration created a successor table, nothing cut over" pattern W1 flagged for `core.llm_provider_configs` specifically, just visible again here at the usage-table level. Worth flagging once, centrally, rather than per-workstream.
- **For whoever reconciles feature-inventory vs. actual AI/LLM spend:** F-5.7's finding (several "AI"-named scoring functions are plain weighted-sum heuristics, no model or LLM) matters for scoping — a spend/risk inventory built from function names alone would overcount how many features carry real LLM cost or data-handling exposure.
