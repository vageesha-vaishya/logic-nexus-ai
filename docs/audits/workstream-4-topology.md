## Findings

### F-4.1 — `services/llm-gateway` has zero live deployment footprint anywhere observed [Low]
**What:** The standalone `services/llm-gateway` package (has its own `Dockerfile`) is not wired into the root `docker-compose.yml`, is not one of the 25 Coolify applications, and no container matching it exists on `hostinger-vps`.
**Evidence:** `grep -n "llm-gateway:" docker-compose.yml` → no match. Coolify `GET /api/v1/applications` (25 results, names extracted) → no `llm-gateway` entry. `ssh hostinger-vps "docker ps -a --format '{{.Names}}\t{{.Status}}' | grep -iE 'llm-gateway|llm_gateway'"` → exit code 1, zero matches, checked against the full ~70-container list.
**Observed or inferred:** Observed (absence across three independent sources).
**Impact:** Confirms, from the deployment side, W1's code-side finding that this service is inert scaffolding rather than a running system in this environment.

### F-4.2 — `services/timesfm-service` exists only in the local/dev compose stack, not in production [Low]
**What:** `timesfm-service` is defined in root `docker-compose.yml` (port `8098:8080`, `container_name: timesfm-service`) but is absent from the Coolify application list and from every running/stopped container on `hostinger-vps`.
**Evidence:** `docker-compose.yml:114-122`; Coolify applications list (25 entries, no `timesfm`); `docker ps -a` grep for `timesfm` → zero matches.
**Observed or inferred:** Observed.
**Impact:** Any code path that assumes this service is reachable in production (e.g., a forecasting feature) would fail or silently no-op there; scope for W5 to confirm whether anything actually calls it.

### F-4.3 — `services/markets-worker` has two declared deployment targets; only one is confirmed live [Medium]
**What:** `markets-worker` is confirmed running on Coolify (`hostinger-vps`), but the service directory also ships a `fly.toml` targeting a separate Fly.io app (`logic-nexus-markets-worker`, region `sin`, "personal-use phase" comment, `min_machines_running = 0`). No `FLY_API_TOKEN` or similar was found in the local repo `env` to check Fly's own state.
**Evidence:** Coolify app `markets-worker` (uuid `biziai4qublf34p3rgiqp22z`), `running:unknown`, container `biziai4qublf34p3rgiqp22z-083047027328` "Up 3 days" per `docker ps`. `services/markets-worker/fly.toml:1-17`. `grep -oE '^[A-Z_]+=' env | grep -i "^FLY"` → no output.
**Observed or inferred:** Observed (Coolify liveness); inferred that the Fly.io target's current state is unknown, not that it is definitely stale — reasoning: a `fly.toml` alone does not prove an active deployment, but it also does not prove the opposite.
**Impact:** If both targets are ever live simultaneously with divergent env/config, that is a duplicate/ungoverned AI-consumer path (two processes independently spending `OPENAI_API_KEY`/`GOOGLE_API_KEY` budget). Needs a Fly.io-side check outside this audit's credential access to resolve.

### F-4.4 — vLLM rig's `/healthz` is unauthenticated and discloses internal GPU/proxy telemetry [Medium]
**What:** Every other probed endpoint on the rig requires bearer auth (401 without it), but `GET /healthz` returns `200` with a JSON body exposing per-GPU temperature, power draw, power limit, clock speed, fan percentage, utilization, a `"hot": true` / `"alert": true` thermal-warning flag, and the fronting Node.js proxy's uptime and memory stats.
**Evidence:** `curl -s -D - https://vllm.sosservices.online/healthz` → `HTTP/1.1 200 OK`, body: `{"timestamp":"2026-09-05T04:46:34.460Z","proxy":{"...":"ok","proxy_uptime":5662.29,...},"vllm":{"status":"ok","http_code":200},"gpu":{"status":"data_available",...,"alert":true,...,"gpus":[{"index":0,"temp_c":93,...,"hot":true},{"index":1,"temp_c":90,...,"hot":true}]},"overall":"healthy"}` (values reproduced here are operational telemetry, not credentials). By contrast `GET /health` (no `z`) on the same host returned `401`.
**Observed or inferred:** Observed.
**Impact:** Anyone on the internet can watch this rig's real-time GPU thermal/utilization state without any credential — useful reconnaissance for timing a denial-of-service attempt against a shared GPU resource, and inconsistent with the auth posture applied to every other endpoint on the same host (including the near-identically-named `/health`).

### F-4.5 — vLLM rig's unauthenticated root page discloses the control-token env var name and control API shape [Low]
**What:** `GET /` returns a 200 HTML/JS "vLLM rig control" page with no auth required. It does not leak a credential value, but its JS names the expected bearer-token environment variable (`OLLAMA_PROXY_TOKEN`) in a UI placeholder, stores the operator-entered token in browser `localStorage`, and documents two control endpoints (`/control/status`, `POST /control/switch` for changing which model/engine is served).
**Evidence:** `curl -s https://vllm.sosservices.online/` → HTML containing `<input id="token-input" type="password" placeholder="Bearer token (OLLAMA_PROXY_TOKEN)">` and JS calling `api('/control/status')` / `api('/control/switch', {method:'POST', body: JSON.stringify({mode})})`. Both `/control/status` (`GET`) and the completion-adjacent endpoints returned `401 {"error":"unauthorized"}` without the token, confirming the surface is gated even though its existence and shape are visible unauthenticated. `OLLAMA_PROXY_TOKEN` does not appear anywhere in this repo (`grep -rn "OLLAMA_PROXY_TOKEN"` → zero hits), confirming this control plane lives outside the `logic-nexus-ai` codebase entirely.
**Observed or inferred:** Observed.
**Impact:** Low direct risk (no bypass attempted or found — this repo's constraints prohibit that), but it hands a would-be attacker the exact env var name and API shape to target if the token ever leaks elsewhere, and it confirms this rig's control plane is a separate, externally-operated system this project only consumes.

### F-4.6 — No per-tenant credential/quota segregation on the default vLLM fallback path [Medium]
**What:** `_shared/llm-gateway.ts`'s env-var fallback to the vLLM rig uses one shared `VLLM_API_KEY`/`VLLM_BASE_URL`/`VLLM_MODEL_NAME` triple for the entire self-hosted deployment. Per-tenant isolation exists only as an opt-in: a tenant row in `platform.llm_provider_configs` may set its own `base_url`/`api_key` for a `local-qwen`-shaped provider, but nothing forces that — any tenant without an explicit override shares the one deployment-wide credential and, by extension, the one rig's GPU quota.
**Evidence:** `supabase/functions/_shared/llm-gateway.ts:297-311` (env fallback construction) and the code comment at lines 19-22: `"local-qwen — OpenAI-compatible chat completions against a self-hosted vLLM (or similar) endpoint. Per §9.6 (D-11): tenant configs may also set this provider directly with their own base_url/api_key."`
**Observed or inferred:** Observed (the fallback construction); inferred that most tenants use the shared fallback rather than a custom override, since verifying actual row contents of `platform.llm_provider_configs` is W1 Step 6's territory, not queried here.
**Impact:** One noisy or compromised tenant on the default path can exhaust the shared rig's GPU capacity or bearer token for every other tenant on that same fallback; there is no rig-side or gateway-side per-tenant rate limiting evidenced here.

### F-4.7 — `VITE_OPENAI_API_KEY` is a client-inlined credential path — currently unset in production, but High by design [High]
**What:** Two frontend call sites read `import.meta.env.VITE_OPENAI_API_KEY` as a "client-side OpenAI fallback" when the Supabase-routed call fails, and would send it directly from the browser to `api.openai.com` if a value were ever set. It is confirmed **not currently set** in the frontend Coolify application's build environment, so there is no live key exposure today — but the code path is live and would activate immediately if that env var were ever populated in that Coolify app.
**Evidence:** `src/hooks/useAiAdvisor.ts:40` — `const clientSideKey = import.meta.env.VITE_OPENAI_API_KEY;` guarded by `clientSideKey.startsWith('sk-')`. `src/features/module-communications/components/email/EmailToLeadDialog.tsx:182` — same pattern. Confirmed absence: Coolify `GET /api/v1/applications/b2lt2if6x6ovekc4tj7vg8tx/envs` (frontend app), full key list filtered for `VITE_`/AI keywords → `VITE_ENABLE_OAUTH, VITE_MARKETS_WORKER_TARGET, VITE_MARKETS_WORKER_URL, VITE_SUPABASE_ANON_KEY, VITE_SUPABASE_PROJECT_ID, VITE_SUPABASE_PUBLISHABLE_KEY, VITE_SUPABASE_URL` — no `VITE_OPENAI_API_KEY` present.
**Observed or inferred:** Observed (both the code path and the current absence from the build env).
**Impact:** Per this audit's severity rule, any `VITE_*` variable holding a provider key is High by construction regardless of current live state, because the class of exposure (any browser can read it) is the defect, not just today's configuration. This is a landmine: a future well-intentioned "just set the env var to unblock the fallback" change would leak a real OpenAI key to every visitor's browser.

### F-4.8 — Anthropic and Mistral provider keys are provisioned nowhere, despite code-level support [Informational]
**What:** Neither the local repo `env`, nor the self-hosted stack `.env` on `hostinger-vps`, nor any of the 25 Coolify applications' env stores contain an `ANTHROPIC_API_KEY` or a Mistral key, even though `services/llm-gateway` lists `anthropic`/`mistral` among its supported providers (per the plan's known facts) and `_shared/llm-gateway.ts` names Anthropic in its routing fallback chain.
**Evidence:** `grep -oE '^[A-Z_]+=' env | grep -iE "anthropic|mistral"` → no output. `ssh hostinger-vps "grep -oE '^[A-Z_]+=' /data/coolify/applications/i64jlyerora7ao9vkw5sweh3/.env | grep -iE 'anthropic|mistral'"` → no output. All 25 Coolify apps' `envs` API responses, key field filtered for `anthropic`/`claude`/`mistral` → no matches. `deploy/selfhosted-supabase/README.md:1240-1244`: `"ANTHROPIC_API_KEY — not provisioned; superseded by the VLLM_* self-hosted fallback above per this project's direction to run LLM workloads against the self-hosted rig instead of a cloud Anthropic subscription."`
**Observed or inferred:** Observed (absence across all three stores), corroborated by an explicit documented decision.
**Impact:** None on its own — this is a deliberate architectural choice, not a gap. Recorded because it explains why `_shared/llm-gateway.ts`'s Anthropic-first routing always falls through to the vLLM rig in this deployment (see W1 for the routing logic itself).

### F-4.9 — Provider API keys were not included in the 2026-09-01 credential rotation [Medium]
**What:** Per this audit's brief, this project rotated `JWT_SECRET`, `ANON_KEY`, `SERVICE_ROLE_KEY`, and the Coolify DB password on 2026-09-01. `OPENAI_API_KEY`, `GOOGLE_API_KEY`, and the `VLLM_*` credentials were not part of that rotation. Consistent with that: the same key **names** (not compared by value) are present identically in both the local repo `env` and the self-hosted stack `.env`, with no separate post-2026-09-01 provider-key rotation event documented anywhere found in this repo.
**Evidence:** Task brief `H:/Projects/logic-nexus-ai/.superpowers/sdd/2026-09-05-ai-llm-audit/task-4-brief.md` Step 5 (stated as ground truth by the controller). Corroborating name-level match: local `env` → `GOOGLE_API_KEY, OPENAI_API_KEY, VITE_OPENAI_API_KEY, VLLM_BASE_URL, VLLM_API_KEY, VLLM_MODEL_NAME`; self-hosted `.env` → `OPENAI_API_KEY, GOOGLE_API_KEY, VLLM_BASE_URL, VLLM_API_KEY, VLLM_MODEL_NAME`. No rotation runbook or log entry for these specific keys found (see Unknowns — I did not find any document recording *why* the 2026-09-01 rotation excluded provider keys).
**Observed or inferred:** The rotation-exclusion fact itself is taken as given per the brief (not independently re-derived); the name-level consistency across stores is directly observed.
**Impact:** If the incident that triggered the 2026-09-01 rotation also touched provider-key-adjacent surfaces (logs, transcripts, a shared `.env`), those provider keys remain exactly as exposed as they were before the rotation. This is the primary input sub-project C needs from this workstream.

## Unknowns / not verified

- **vLLM rig's true origin host.** DNS for `vllm.sosservices.online` resolves only to Cloudflare-proxy IP ranges (`104.21.20.144`, `172.67.192.248`, plus two IPv6 addresses); the actual origin server's location (co-located with `hostinger-vps` behind a tunnel, or a fully separate physical GPU host) cannot be determined from outside Cloudflare's edge with the tools available here.
- **Whether the rig is genuinely "shared" across other SOS Services products.** None of the other 24 Coolify applications on `hostinger-vps` (including `avaipro-*`, `sthira-marketing`, `aviation-ai-pro-marketing`) have any `VLLM_*` env var set, so I could not confirm from this vantage that products beyond `logic-nexus-ai` actually send it traffic — only that the domain name and control-panel design (multi-mode switching) are consistent with shared, multi-consumer infrastructure.
- **Whether `services/markets-worker`'s Fly.io target (`fly.toml`) is currently deployed and receiving traffic.** No Fly.io API token was found in the local repo `env` to query Fly's own state; this needs Fly-side credentials not available to this audit.
- **Whether OpenAI/Google/vLLM keys have ever appeared in live Coolify build or deploy logs.** I searched this repo's tracked docs, SDD reports, and stray untracked root log files for leaked key patterns (`sk-...`, `AIza...`) and found none, but I did not query Coolify's own build-log API end-to-end for these apps — that would require pulling and grepping potentially large log bodies, which the secret-handling constraints caution against doing broadly, and time did not permit a fully scoped per-app pass.
- **Full git history.** A `git log --all -S"sk-"` pickaxe search across the entire history timed out after 2 minutes and did not complete; I cannot rule out a historical (already-rotated-out, or not) key committed and later removed from HEAD.
- **Contents of `platform.llm_provider_configs`.** Whether any tenant rows actually set a custom vLLM `base_url`/`api_key` (which would mean real per-tenant segregation exists in practice, not just in theory) is W1 Step 6's territory and was not queried here.
- **Why the duplicate key entries appeared in three Coolify apps' `envs` API responses** (e.g., `logicnexus-selfhost-supabase`'s AI keys each listed twice). Plausibly separate production/preview environment scopes in Coolify's data model, but not confirmed.
- **Operational key-issuance process for the vLLM rig's own `OLLAMA_PROXY_TOKEN`/`VLLM_API_KEY`.** No runbook for how these are minted, stored, or rotated exists anywhere in this repository — that process, if it exists, lives entirely in the externally-operated rig's own (inaccessible) documentation.
