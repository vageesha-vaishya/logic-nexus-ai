## Findings

### F-1.1 — The 863-LOC edge-function gateway is the one actually serving production traffic; the 6,726-LOC Express service has never run [High]
**What:** `platform.llm_provider_configs`'s `is_default=true` row (`provider = gemini`) shows `last_used_at = 2026-09-01 06:47:04+00`, and only `supabase/functions/_shared/llm-gateway.ts` ever calls the RPC (`platform.get_tenant_llm_config`) that updates that column. `services/llm-gateway` has no Dockerfile entry in any compose file and no matching container among 78 on the VPS. So the smaller, far-less-governed implementation is authoritative in production today, and the larger, control-rich implementation is inert.
**Evidence:** `ssh hostinger-vps "docker exec db-i64jlyerora7ao9vkw5sweh3-151315142961 psql -U postgres -d postgres -c \"select provider,is_active,is_default,last_used_at from platform.llm_provider_configs;\""` → `gemini | t | t | 2026-09-01 06:47:04.766+00`; `ssh hostinger-vps "docker ps -a --format '{{.Names}}\t{{.Image}}' | grep -i llm"` → no output; `services/llm-gateway/` has `Dockerfile` but `grep -rn "llm-gateway" docker-compose.yml` → no match.
**Observed or inferred:** Observed (both the recent-use timestamp and the absence of any deployed container are direct command output); the causal link "edge function is what updated that timestamp" is inferred from the fact it is the only code path in the repo that calls `get_tenant_llm_config`.
**Impact:** This is the workstream's headline fact. Every governance capability the Express service has (below) is currently providing zero protection in production, because it isn't running.

### F-1.2 — The live gateway has no PII redaction and no budget enforcement of its own; both exist only in the unused service [High]
**What:** `services/llm-gateway/src/routes/invoke.ts` redacts `InvokeRequest.variables` via `pii/redactor.ts` **before** the provider is resolved or called, and performs a pre-call budget-cap check (`budgets/enforcement.ts`) that rejects with HTTP 429 (`BUDGET_EXCEEDED`/`QUOTA_EXCEEDED`) **before** `provider.invoke()` runs. `supabase/functions/_shared/llm-gateway.ts` contains none of this: grepping the whole 863-line file for `pii|redact|budget|quota` returns exactly 2 hits — a comment ("we keep the budget consistent...") and the type-literal `"budget_exceeded"` in a `status` union that is **never assigned anywhere in the file**. Auth for the edge path is not inside the gateway module at all; each of the 4 callers (`markets-*` functions) independently wires `requireAuth`/`checkDomainAccess`/`checkRateLimit` around their own call to `callLLM()`.
**Evidence:** `services/llm-gateway/src/routes/invoke.ts` (PII redaction precedes `cascadeResolve`; budget check precedes `resolveProvider`/`provider.invoke`, both before the `provider.invoke(safeRequest, ctx)` call); `grep -in "pii|redact|budget|quota|scope|rtbf|forgotten|fine.?tun|embed" supabase/functions/_shared/llm-gateway.ts` → only lines 64 (comment) and 639 (unused enum literal); `supabase/functions/markets-portfolio-brief/index.ts:27-30` imports `requireAuth`, `checkDomainAccess`, `checkRateLimit` alongside `callLLM`.
**Observed or inferred:** Observed.
**Impact:** Real user data (portfolio holdings, tracked symbols, conversational research-thread messages) flows through the live gateway with no redaction and no automatic spend ceiling. Protection today depends entirely on each of the 4 callers never regressing their own auth/rate-limit wiring — there is no chokepoint enforcement, unlike the unused Express service which is designed as one.

### F-1.3 — "vLLM" means two different things across the two implementations; one is a dead type reference [Low]
**What:** In `services/llm-gateway`, `'vllm'` appears only in the `ProviderKind` type union (`types/gateway.types.ts`) and in a roadmap comment in `providers/index.ts` ("P3 onwards ollama / vllm / azure_openai"). It is **not** present in the provider registry object, so `resolveProvider('vllm')` would throw `PROVIDER_NOT_CONFIGURED:vllm`, and no resolver/cascade logic ever produces `provider_kind: 'vllm'` — it is a type-only placeholder for unbuilt future work, not dead-but-reachable code. In `supabase/functions/_shared/llm-gateway.ts`, the equivalent capability is real (if currently unreached — see below) under the name `local-qwen`: when no tenant config and no `ANTHROPIC_API_KEY` are available, it falls back to an OpenAI-compatible endpoint at `VLLM_BASE_URL` using `VLLM_API_KEY`/`VLLM_MODEL_NAME`.
**Evidence:** `grep -n "vllm" services/llm-gateway/src/providers/index.ts services/llm-gateway/src/types/gateway.types.ts` → `index.ts:2` (comment only), `gateway.types.ts:11` (`| 'vllm'` in the type union only) — confirmed the registry object at `index.ts:15-21` has no `vllm` key; `supabase/functions/_shared/llm-gateway.ts:297-312` (`local-qwen` env fallback); live: `ssh hostinger-vps "docker exec functions-i64jlyerora7ao9vkw5sweh3-151315126444 env | grep -oE '^[A-Z_]+=' | grep VLLM"` → `VLLM_API_KEY=`, `VLLM_BASE_URL=`, `VLLM_MODEL_NAME=` (names present; values not read, per secret-handling rules — set-vs-unset was not distinguished since `${VLLM_BASE_URL:-}` defaults to empty in the compose file, so presence of the name alone does not prove a real value is set).
**Observed or inferred:** Observed for both grep results; inferred that the `local-qwen` fallback path is not actually being exercised today, from the fact the live default provider row is `gemini` (tenant-config path wins before the fallback chain is reached) — not independently confirmed by tracing a live request.
**Impact:** Anyone grepping "vllm" in this codebase to answer "does self-hosted LLM support exist" gets a false negative from the service (dead type) and has to know to look for `local-qwen` in the edge function instead. This is exactly the kind of cross-implementation naming drift the audit exists to surface — recommend Task 4 (vLLM rig workstream) confirm whether `VLLM_BASE_URL` actually resolves to a live endpoint, since that is outside this workstream's scope.

### F-1.4 — Express service's service-token auth defaults to fully open unless an operator explicitly sets `LLM_GATEWAY_AUTH_MODE=enforced` [High]
**What:** `buildAuthLookup()` treats the absence of both `LLM_GATEWAY_DEV_TOKENS` and Supabase env vars (or an explicit `LLM_GATEWAY_AUTH_MODE=open`) as "OPEN MODE": every call returns `{authenticated: true, open_mode: true}`, and `middleware/auth.ts`'s `requireScope()` short-circuits scope + `X-Platform-Id` checks whenever `open_mode` is set. A code comment states "Production explicitly sets `LLM_GATEWAY_AUTH_MODE=enforced`," but nothing in the codebase enforces that at deploy time — it is operator discipline, not a code-level guarantee. The service is not currently deployed (F-1.1), so this is dormant, not exploited.
**Evidence:** `services/llm-gateway/src/auth/serviceToken.ts` (`buildAuthLookup`, the `explicitMode === 'open' || (!devTokens && !supabaseEnv && explicitMode !== 'enforced')` branch); `services/llm-gateway/src/middleware/auth.ts` (`if (result.open_mode) return next();` skips scope check entirely).
**Observed or inferred:** Observed.
**Impact:** Matches the audit's "High" bar exactly ("a latent trap one config change away from Critical"): whenever this service is eventually deployed, a single missing environment variable turns it into a fully open LLM-invocation endpoint for anyone who can reach it on the network — no code change required to cause a Critical-severity exposure.

### F-1.5 — Two live tables named `llm_provider_configs` in different schemas; an unqualified `pg_policies` query (as literally given in the audit brief) silently merges their policy sets [Low]
**What:** A migration (`20260528130400_create_core_llm.sql`, "Phase 1.5 — core.llm_* (lift from platform.*)") creates `core.llm_provider_configs` as an intended successor to `platform.llm_provider_configs` (adds `mistral`/`cohere` providers and a `rate_limit_qps` column). It is live in the DB but has 0 rows — no consumer has cut over. Running the brief's literal Step 6 command, `select policyname, cmd, qual from pg_policies where tablename='llm_provider_configs'` (no `schemaname` filter), returns 5 rows that at first glance look like one table's RLS policy set, but are actually 4 policies on `platform.llm_provider_configs` plus a broader `FOR ALL` policy (`llm_configs_tenant_admin_all`) that belongs to `core.llm_provider_configs`. Re-running with `schemaname` included resolves the ambiguity.
**Evidence:** `select schemaname, tablename, policyname, cmd from pg_policies where tablename='llm_provider_configs' order by schemaname, policyname;` → `core|llm_provider_configs|llm_configs_tenant_admin_all|ALL` plus 4 `platform|llm_provider_configs|...` rows; `select count(*) from core.llm_provider_configs;` → `0`; migration file `supabase/migrations/20260528130400_create_core_llm.sql:17-34` (table def), `:193` (the `ALL` policy).
**Observed or inferred:** Observed.
**Impact:** Low direct impact today (the `core` table is empty and unused), but this is a live, reproducible instance of exactly the "casual query looked right but wasn't" trap the audit's own Evidence Standard section warns about. Flag for whichever workstream/synthesis step inventories DB schema drift — a `platform` → `core` schema migration is in flight for at least this table family.

### F-1.6 — RTBF/erasure exists only in the unused service; the live edge-function gateway has no erasure path at all [Medium]
**What:** `services/llm-gateway/src/rtbf/store.ts` calls a real Postgres RPC, `gateway.scrub_subject_pii(...)` (defined in `supabase/migrations/20260603090000_gateway_rtbf.sql`), gated behind the `admin_configs` scope at `POST /v1/admin/right-to-be-forgotten`. Since the service has never been deployed (F-1.1), this working deletion path has never executed against real data. `supabase/functions/_shared/llm-gateway.ts` has no RTBF/erasure logic or endpoint of any kind — a GDPR Art. 17 request against `markets.briefs`/`platform.llm_usage` rows tied to a real user has no automated purge path today in the implementation that is actually live.
**Evidence:** `services/llm-gateway/src/rtbf/store.ts` (`buildSupabaseRtbfStore` → `client.rpc('scrub_subject_pii', ...)`); `services/llm-gateway/src/routes/rtbf.ts` (`requireScope('admin_configs', ...)`); `supabase/migrations/20260603090000_gateway_rtbf.sql` (RPC definition confirmed to exist); `grep -in "rtbf|forgotten" supabase/functions/_shared/llm-gateway.ts` → no matches.
**Observed or inferred:** Observed.
**Impact:** The production LLM path that actually writes user-identifiable rows (`markets-portfolio-brief` inserts into `markets.briefs`, tied to `tenant_id`/portfolio ownership; `platform.llm_usage` carries `tenant_id`/`user_id`) has no corresponding erasure mechanism. Any RTBF obligation touching markets-domain LLM data would require a manual, ad hoc process today.

## Unknowns / not verified

- Whether `services/llm-gateway` was ever deployed in the past and later decommissioned, versus never deployed at all — only its current absence was confirmed, not its deployment history (no access to Coolify's deployment-history log was attempted, per the read-only/no-extra-API-calls posture, and it wasn't in scope to chase further).
- Whether `VLLM_BASE_URL`/`VLLM_API_KEY`/`VLLM_MODEL_NAME` on the live functions container hold real (non-empty) values or resolve to the compose file's empty `${VAR:-}` default — only the variable **names** were confirmed present, per the secret-handling rule against dumping env values; distinguishing "set to a real endpoint" from "set to empty string" would require reading a value, which this audit does not do. Recommend Task 4 (vLLM rig workstream) resolve this from their own angle.
- Whether any request has ever actually taken the `local-qwen`/vLLM fallback branch in `_shared/llm-gateway.ts` in production, versus always resolving via the `gemini` tenant config — inferred as "never/rare" from the tenant-config row's `is_default=true` and recent `last_used_at`, but not confirmed by reading function logs (out of scope: the brief's method limits call for config inspection, not log-diving for request-level proof).
- Whether `core.llm_provider_configs` (F-1.5) has any consumer code already written but not yet cut over (e.g. a half-finished PR), or is purely a schema-only placeholder — only the live row count (0) and the migration file's stated intent were checked; the broader `core.*` schema/`@platform/llm-client` migration effort was not traced.
- Exact current row-level `metadata`/`base_url` contents of the 2 `platform.llm_provider_configs` rows were not inspected beyond `provider/is_active/is_default/last_used_at`, since the `vault_secret_name` column is adjacent to secret material and querying it felt like an unnecessary approach to sensitive-adjacent data for a fact not needed by this workstream's questions.
- Whether the `services/llm-gateway` service passes its own test suite / has ever been smoke-tested end-to-end — not run, per the strictly-read-only / no-execution posture of this audit.

A naive "the bigger/newer one must be the real one" assumption would get this backwards.
