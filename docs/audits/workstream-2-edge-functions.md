# Workstream 2: Edge function AI/LLM surface sweep

## Scope covered

- `supabase/functions/` in full: 152 function directories (plus `_shared/`, `deno.json`, `import_map.json`, `types.d.ts` — 156 top-level entries total, which is where the brief's "156" figure comes from; 152 is the correct denominator for "functions").
- Every function checked by **behavior**, not name, via a layered grep sweep, each layer's hits individually opened and read:
  1. Provider keyword/hostname content grep (`openai|anthropic|gemini|claude-|gpt-4|gpt-3`, plus a second pass for `groq|together|openrouter|replicate|huggingface|cohere|perplexity|bedrock|vertexai|ollama|ai21|stability|elevenlabs|deepseek|x\.ai|grok|vllm|azure.*openai`) — 20 + 1 hits.

  4. `Deno.env.get(...)` scan for any `*API*|*LLM*|*MODEL*|*AI*|*GPT*|*EMBED*|*VISION*|*OPENAI*|*ANTHROPIC*|*GEMINI*|*VLLM*|*GROQ*` variable name, and separately for every `*URL*` env var — surfaced `LLM_GATEWAY_URL` (16 functions) and `TIMESFM_URL` (2 functions) as pathways not caught by (1)-(3).

## Headline numbers

- **38 of 152 edge functions actually call an AI/ML model** (behaviorally confirmed — see table). A further 14 functions were individually verified to be **false positives** that a naive name or keyword match would flag (see Findings F-2.6/F-2.7).
- Of those 38, **15 (39%) call a third-party provider directly with zero shared layer** — no `_shared/llm-gateway.ts`, no `_shared/model-router.ts`, no gateway microservice. **This is the shadow-AI bucket the workstream exists to size.**
- Only 8 of the 38 (`markets-enrich-news`, `markets-portfolio-brief`, `markets-portfolio-diagnostic`, `markets-research`, `classify-email`, `generate-embedding`, `ingest-email`, and half of `nexus-copilot`) route through either of the two known local shared modules.
- 16 functions (all 15 `llm-*` functions plus `container-demand`) route through some other internal layer — but 15 of those 16 target an external microservice (`services/llm-gateway`, via `LLM_GATEWAY_URL`) that Workstream 1 confirmed is **never deployed anywhere** (no container, no compose entry) — so that entire branch is currently dormant, not "governed."
- 2 Critical-severity findings: `ai-advisor` and `generate-embedding` are both publicly invocable (no enforced auth) AI functions that touch backend data with a service-role client and are **live on the self-hosted production stack today**.

## Findings

### F-2.1 — `ai-advisor` is a live, publicly-invocable AI function that queries cross-tenant pricing data with a service-role client [Critical]
**What:** `ai-advisor`'s auth check does not gate execution: `const { user, error: authError } = await requireAuth(req); if (authError || !user) { logger.warn("Auth failed, continuing in anonymous mode", ...); }` — there is no `return` in that branch, so the function keeps running as an unauthenticated caller. Its `generate_smart_quotes` action then queries `rates` (`.from('rates').select('base_price').eq('mode', mode).ilike('origin', ...).ilike('destination', ...)`) with the service-role client passed into `serveWithLogger` — the query has no `tenant_id`/`franchise_id` filter anywhere in the file (`grep -n "tenant_id\|tenantId"` returns zero query-scoping hits). The averaged historical price is embedded directly into the OpenAI prompt and the AI-generated quote (informed by that internal pricing) is cached in `ai_quote_cache` and returned to the caller. `ai_quote_cache` inserts `user_id: userId ?? null`, confirming anonymous use is an anticipated code path, not an overlooked edge case.
**Evidence:** `supabase/functions/ai-advisor/index.ts:50-53` (auth-failure branch has no early return); `:262-268` (`rates` query, no tenant filter); `:416,425` (`ai_quote_cache` insert with `user_id: userId ?? null`); `supabase/config.toml:203-204` (`[functions.ai-advisor] verify_jwt = false`); `ssh hostinger-vps "grep FUNCTIONS_VERIFY_JWT /data/coolify/applications/i64jlyerora7ao9vkw5sweh3/.env"` → `FUNCTIONS_VERIFY_JWT=false`; `docker exec functions-i64jlyerora7ao9vkw5sweh3-151315126444 ls /home/deno/functions` → `ai-advisor` present (live on self-host).
**Observed or inferred:** Observed — every step (missing return, unscoped query, live deployment, global JWT-off) is direct code/config/command evidence. That the `rates` table actually contains data from more than one tenant was not independently queried against the live DB (that would be a DB-side check outside this workstream's edge-function-code scope) — inferred from the absence of any tenant filter in the query that would otherwise be required for correct multi-tenant behavior.
**Impact:** Meets the brief's Critical bar exactly ("publicly invocable... and also returns or accepts tenant data"). An anonymous caller can (a) exfiltrate a signal about internal historical freight pricing across tenants via the AI-generated quote text, and (b) spend the org's OpenAI budget for free, repeatedly, with no rate limit observed in this file. This is deployed and live today, not hypothetical.

### F-2.2 — `generate-embedding` has no authentication of any kind and lets anonymous callers spend AI budget on arbitrary text [Critical]
**What:** The function has no `requireAuth`, no `requireServiceRoleOrAdmin`, and no role check — `serveWithLogger` hands it a service-role Supabase client directly, and it's used unconditionally as `const admin = supabase`. With `payload.text` set, any caller (no credentials) gets `{ embedding: emb }` back for arbitrary submitted text — free, unmetered embedding-API access. With `payload.batch`, any caller can trigger processing of up to `payload.limit` (max unbounded, no server-side cap on the value) rows from `knowledge_base` or `master_hts` in one call. `verify_jwt` has no per-function override for this function in `config.toml`, and the self-hosted stack's JWT verification is globally off (`FUNCTIONS_VERIFY_JWT=false`), so there is no platform-level backstop either.
**Evidence:** `supabase/functions/generate-embedding/index.ts` (full file — no auth import at all, `admin = supabase` at line 35); `supabase/config.toml` has no `[functions.generate-embedding]` block (confirmed via `awk` scan of every `[functions.*]`/`verify_jwt` pair); `ssh hostinger-vps "grep FUNCTIONS_VERIFY_JWT ...` → `false`; self-host `docker exec ... ls /home/deno/functions` → `generate-embedding` present (live).
**Observed or inferred:** Observed.
**Impact:** Meets Critical: accepts arbitrary caller-supplied data, calls a third-party provider (`OPENAI_API_KEY` via `_shared/model-router.ts`), and is live in production with zero auth. Lower ceiling than F-2.1 (no direct tenant-data return path was found for the `payload.id` branches — they return only `{updated: 1}`), but the `payload.text` branch alone is unrestricted budget-theft-as-a-service.

### F-2.3 — 15 of 38 AI-calling functions (39%) bypass every shared layer — the headline shadow-AI number [High]
**What:** `ai-advisor`, `ai-agent`, `ai-message-assistant`, `analyze-cargo-damage`, `analyze-email-threat`, `categorize-document`, `ensemble-demand`, `extract-bol-fields`, `extract-invoice-items`, `forecast-demand`, `nexus-copilot` (partially — see F-2.4), `portal-chatbot`, `route-optimization`, `smart-reply`, and `suggest-transport-mode` all call `api.openai.com` or `generativelanguage.googleapis.com` directly via raw `fetch()`, reading `OPENAI_API_KEY`/`GOOGLE_API_KEY` straight from `Deno.env.get(...)` in the function's own file. None import `_shared/llm-gateway.ts` or `_shared/model-router.ts`. Of these 15, only 7 (`ai-advisor`, `ai-agent`, `ensemble-demand`, `nexus-copilot`, `portal-chatbot`, `route-optimization`, `smart-reply`) import `_shared/pii-guard.ts`; the other 8 send data straight to the provider with no PII scrubbing at all — and several of those 8 process customer/business documents by name (`extract-bol-fields` = bills of lading, `extract-invoice-items` = invoices, `categorize-document` = arbitrary uploaded documents, `analyze-cargo-damage` = cargo photos, `analyze-email-threat` = email content).
**Evidence:** Per-function `grep -n "api.openai.com\|generativelanguage.googleapis.com"` hits listed in the per-function table above; `grep -rl "_shared/pii-guard" supabase/functions/` → 12-file list cross-referenced against the 15.
**Observed or inferred:** Observed for the fetch/import evidence. That the unscrubbed 8 actually carry PII in practice (vs. always-clean synthetic inputs) is inferred from each function's stated purpose (document/photo/email extraction) rather than from inspecting live payloads.
**Impact:** This is the number Task 6's fragmentation map needs. No cost ceiling, no centralized audit trail, no PII policy, and no provider-swap capability (e.g., the recent self-hosted vLLM fallback work in `_shared/llm-gateway.ts` does not benefit any of these 15) apply to over a third of the platform's AI surface.

### F-2.4 — `nexus-copilot` imports a shared helper but still bypasses it for the actual generation call — import-checking alone understates the shadow-AI count [Medium]
**What:** `nexus-copilot` imports `_shared/model-router.ts` (`pickEmbeddingModel`) and uses it correctly for the embedding step, which would make it look "governed" under a naive per-file import check. But its actual chat/completion call — the part that generates the copilot's answer — is a direct `fetch("https://api.openai.com/v1/chat/completions", ...)` with `Deno.env.get("OPENAI_API_KEY")`, entirely outside `model-router.ts` or `llm-gateway.ts`.
**Evidence:** `supabase/functions/nexus-copilot/index.ts:4` (`import { pickEmbeddingModel } from "../_shared/model-router.ts"`), `:49` (`fetch(url, ...)` using the router's output for embeddings), `:81-82` (`Deno.env.get("OPENAI_API_KEY")` then `fetch("https://api.openai.com/v1/chat/completions", ...)`).
**Observed or inferred:** Observed.
**Impact:** Methodology note for Task 6: "imports a shared AI helper" is necessary but not sufficient evidence a function is fully governed — per-call-site verification (as done here) is required, not per-file import scanning. Counted in F-2.3's 15.

### F-2.6 — `portal-chatbot` is intentionally public and can be invoked to spend AI budget with no credentials [High]
**What:** The function explicitly swallows auth failures: `try { const auth = await requireAuth(req); user = auth.user; } catch { /* ignore auth errors for public portal */ }`. It then calls OpenAI embeddings + `gpt-4o-mini` chat directly (B4). Tenant-specific quote context is gated behind a caller-supplied opaque `token` passed to the `get_quote_by_token` RPC (not blanket tenant exposure), and it does call `sanitizeForLLM` before building the prompt — so this is deliberately scoped-down public access, not an oversight, and does not meet the "returns/accepts tenant data" bar for Critical the way F-2.1 does.
**Evidence:** `supabase/functions/portal-chatbot/index.ts:17-22` (swallowed auth), `:44` (`get_quote_by_token` RPC, token-gated), `sanitizeForLLM` import line 4; `config.toml` `[functions.portal-chatbot] verify_jwt = false`; self-host deployment confirmed (present in container listing).
**Observed or inferred:** Observed.

### F-2.7 — Config-toml's per-function `verify_jwt` overrides are dead weight on the self-hosted stack; the platform-level check is off for every function, globally, all the time [Medium]
**What:** `deploy/selfhosted-supabase/docker-compose.yml:316` wires the edge-runtime container's `VERIFY_JWT` env var straight from `${FUNCTIONS_VERIFY_JWT}` (a single global flag), and `env.example:122` documents it as `FUNCTIONS_VERIFY_JWT=false`. **Evidence:** `deploy/selfhosted-supabase/docker-compose.yml:316` (`VERIFY_JWT: "${FUNCTIONS_VERIFY_JWT}"`); `deploy/selfhosted-supabase/env.example:122` (`FUNCTIONS_VERIFY_JWT=false`); `ssh hostinger-vps "grep FUNCTIONS_VERIFY_JWT /data/coolify/applications/i64jlyerora7ao9vkw5sweh3/.env"` → `FUNCTIONS_VERIFY_JWT=false`; `supabase/config.toml` 86-entry `verify_jwt` scan (all `false` where present).

### F-2.8 — `forecast-demand`'s "internal model first" fallback defaults to an address that cannot resolve in the edge runtime, making the OpenAI direct-call path the de facto default [Low]

### F-2.9 — Platform-wide default: JWT verification is off for every self-hosted edge function, not just the two AI functions in F-2.1/F-2.2 [High]
**What:** `FUNCTIONS_VERIFY_JWT=false` (confirmed live: `ssh hostinger-vps "grep -o 'FUNCTIONS_VERIFY_JWT=.*' /data/coolify/applications/i64jlyerora7ao9vkw5sweh3/.env"` → `FUNCTIONS_VERIFY_JWT=false`) is a single flag applied uniformly to the entire self-hosted edge-runtime container (F-2.7's wiring: `docker-compose.yml:316`, `VERIFY_JWT: "${FUNCTIONS_VERIFY_JWT}"`). This is not a per-function setting and is not specific to AI functions — it is the platform-level default for **all ~110 functions currently deployed to that container**. F-2.1 (`ai-advisor`) and F-2.2 (`generate-embedding`) are the two *AI-relevant, confirmed-exploitable* instances of this exposure class (their own code additionally fails to gate on auth), but the underlying platform condition they sit on top of is broader: **any** deployed function whose own code does not independently call `requireAuth`/`requireServiceRoleOrAdmin` and hard-fail is equally exposed at the platform layer, whether or not it touches AI. Checking Kong's declarative config (`kong.yml`) for a compensating gateway-level control: the `functions-v1` route (`/functions/v1/*` → `http://functions:9000/`) carries only a `cors` plugin, both in the repo's copy and in the live file on the VPS (`ssh hostinger-vps "grep -n -A 12 'name: functions-v1' /data/coolify/applications/i64jlyerora7ao9vkw5sweh3/kong.yml"`). Kong's `key-auth` plugin (which would require the standard Supabase `apikey` header on every request) **is** applied to six other routes in the same file (`auth-v1`, `rest-v1-openapi`, `rest-v1`, `graphql-v1`, `realtime-v1-ws`, `realtime-v1-rest` — confirmed by `awk` pairing each `key-auth` plugin line to its owning route block) and there is no top-level/global `plugins:` block in the file that could apply to `functions-v1` implicitly (`grep -n '^plugins:'` returns nothing; the file only has a top-level `services:` key). So `functions-v1` is deliberately excluded from Kong's `key-auth` gate — there is no gateway-level apikey requirement compensating for `FUNCTIONS_VERIFY_JWT=false` on this route.
**Evidence:** `ssh hostinger-vps "grep -o 'FUNCTIONS_VERIFY_JWT=.*' /data/coolify/applications/i64jlyerora7ao9vkw5sweh3/.env"` → `FUNCTIONS_VERIFY_JWT=false`; `deploy/selfhosted-supabase/docker-compose.yml:316`; live `kong.yml:354-364` (`functions-v1` service/route, `plugins: [cors]` only) — byte-identical to the repo's `deploy/selfhosted-supabase/kong.yml:354-364`; live `kong.yml` `key-auth` plugin instances at lines 122, 150, 178, 207, 238, 299, each under a different route name, none of them `functions-v1`; `docker exec functions-i64jlyerora7ao9vkw5sweh3-151315126444 ls /home/deno/functions` → ~110 deployed functions, all sitting behind this same route.
**Observed or inferred:** **Observed** (config-only): the `FUNCTIONS_VERIFY_JWT=false` value, the compose wiring, and the absence of any `key-auth`/apikey/jwt plugin on the `functions-v1` Kong route — all read directly from live files, no traffic sent. **Inferred** (and explicitly not proven): that this actually makes every non-self-gating function *publicly reachable over the internet today*. Confirming true end-to-end reachability would require sending a request to a real endpoint from outside the VPS, which the audit's method limits forbid (no exploitation; and for an AI function like `generate-embedding` it would also mean spending real OpenAI credit to prove the point). What is proven is that the two gates that would normally stop an unauthenticated request before it reaches function code — platform-level JWT verification and a Kong-level apikey requirement — are both absent for this route, config-wise. Whether a network-layer control sits further upstream (e.g., a firewall or reverse proxy restricting which source IPs can reach Kong/the VPS at all) was not checked and is a genuine remaining unknown (see Unknowns).
**Impact:** Reframes F-2.1 and F-2.2 as the two *confirmed-exploitable, AI-relevant* instances of a platform-wide exposure class rather than isolated bugs in those two functions. Any other deployed function (AI or not) that similarly omits an in-body `requireAuth`/`requireServiceRoleOrAdmin` hard-fail is, on this same config evidence, equally unprotected by the platform — that broader non-AI inventory is out of this workstream's scope but is exactly the kind of cross-cutting risk Task 6's synthesis should carry forward.

## Post-audit correction (2026-09-05)

This section is appended after publication; it does not alter anything above, which remains the evidentiary record of what this workstream found and inferred at the time from `config.toml`, `FUNCTIONS_VERIFY_JWT`, and Kong's route config.

A post-audit check found that this workstream's reachability analysis — and the synthesis report built on it — missed an entire enforcement layer that was present in the repo the whole time and was never opened: `supabase/functions/main/index.ts`. The self-hosted functions container does not serve functions individually; it runs a single router (`docker inspect` on the live container shows `["start","--main-service","/home/deno/functions/main"]`), and every request passes through it. That router enforces JWT per function against `supabase/functions/main/verify_jwt_map.ts` (85 entries, all `false`), defaulting anything **not** listed to requiring a valid JWT (`main/index.ts:336`, `VERIFY_JWT_MAP[name] !== false`). `verifyJwtSignature` in the same file (`main/index.ts:248+`) is a real implementation — it requires an `Authorization` header, extracts and validates the bearer token, rejects malformed JWTs, enforces `alg === "HS256"`, and verifies the HMAC signature. This is not a stub, and it was not covered anywhere in this workstream's scope list above.

This revises the findings below:

- **F-2.1 (`ai-advisor`, Critical) stands, and its evidence is strengthened.** `ai-advisor` is listed `"ai-advisor": false` in `verify_jwt_map.ts`, so the router's gate is genuinely off for it, and its own body (`ai-advisor/index.ts:50-53`) logs a warning and continues rather than rejecting on auth failure — the finding's anonymous-invocability claim was correct. Two further facts, not available to this workstream's original scope (edge-function code + `config.toml`/Kong only), now make its cross-tenant-read claim **observed** rather than *inferred*: `serveWithLogger` (`_shared/logger.ts:210-211`) builds its Supabase client from `SUPABASE_SERVICE_ROLE_KEY`, bypassing RLS; and the `rates` table has both `tenant_id` and `franchise_id` columns (verified via `information_schema.columns`, outside this workstream's original scope), neither of which the query filters on. This workstream's own Unknowns entry ("Whether the `rates` table... actually contains rows from more than one tenant... this workstream is edge-function-code-scoped and did not query the database directly") correctly flagged the limit of what could be established from this workstream's inputs alone; the additional facts close that gap.
- **F-2.2 (`generate-embedding`, originally Critical here) is downgraded to Medium in the synthesis report.** This workstream's evidence — "no `config.toml` entry (so it inherits the platform default, which is off)" — was accurate as far as `config.toml` and the platform flag go, but incomplete: `generate-embedding` is also absent from `verify_jwt_map.ts`, and the router's own default for anything absent is to *require* a valid JWT, independent of the platform flag. So the router returns 401 to an unauthenticated caller before the function body — which still has no in-body auth check of its own, and still performs the service-role writes this workstream documented — ever runs. It is not anonymously reachable today; see the synthesis report (`2026-09-05-ai-llm-audit-findings.md`) for the full revised finding and severity justification.
- **F-2.9 (platform-wide JWT default, originally High here) is downgraded to Medium in the synthesis report**, and this workstream's F-2.7 framing is superseded. F-2.7 concluded that `config.toml`'s per-function `verify_jwt` overrides are "dead weight on the self-hosted stack" and that "the `verify_jwt=false` column is not the operative control on self-host." That conclusion was reasonable given what this workstream checked (compose/env wiring, no per-function override mechanism visible in those files) but wrong: those overrides are exactly the source data for `verify_jwt_map.ts`, which the `main` router reads and enforces on every request. The map **is** the operative control this workstream was looking for and did not find. F-2.9's own framing — "every deployed function that does not perform its own in-body auth check is affected" — is likewise wrong: only the 85 functions listed `false` in the map skip the router's check.

**Portal-chatbot (F-2.6) is unaffected in substance.** It was already correctly documented as deliberately public, token-scoped, and PII-sanitized; that remains accurate under the corrected model (it is listed `false` in `verify_jwt_map.ts` and its body does not hard-fail on missing auth, matching this workstream's original description).

**Why this workstream missed it:** the scope list above (line 14) covers `config.toml`, the live `FUNCTIONS_VERIFY_JWT` value, and how that flag is wired into the edge-runtime container's environment — all genuine, correctly-read facts about the *platform-level* gate. It does not list reading the edge-runtime's own entrypoint or the function router source (`supabase/functions/main/`) that runs inside it, despite the container filesystem listing (line 15) having already been pulled for a different purpose (per-function deployment presence). This is the same gap the synthesis report's methodology note now records: configuration layers were read without tracing the actual request path.
