# RLS audit — `markets.*` schema · 2026-05-21

Pre-closed-beta security check. Scope: every table in the `markets` schema
on prod (`gzhxgoigflftharcmdqj`). The `retail` schema does not exist —
retail surfaces live under `markets`.

## TL;DR — verdict

**GREEN for closed-beta (friends + family, 10–20 users).** Every table
that holds user data is RLS-enabled and properly scopes by `auth.uid()`.
No cross-user data exposure path found.

Three low-severity findings flagged for fix-before-public-launch:

- **`markets.ai_briefs` INSERT policy** has `WITH CHECK true` — any
  authenticated user can insert briefs claiming any `owner_user_id`.
  SELECT correctly scopes to own briefs so this is data-pollution risk,
  not data-leak risk.
- **`markets.signals_macro_context` INSERT policy** has the same
  `WITH CHECK true` pattern. Same data-pollution risk.
- **`markets.signals_macro_context` SELECT policy** references
  `auth.users.tenant_id`, which does not exist on the `auth.users`
  table. The first branch of the OR is effectively dead-code; only
  `tenant_id IS NULL` rows are visible. The intent was likely to
  scope by tenant — fix when multi-tenant signals matter.

Two cosmetic duplicate-policy findings (no security impact):

- **`markets.holdings`** has 8 policies — 4 redundant pairs (`_owner_*`
  for authenticated role + `_own` for public role), identical
  predicates. Functional but should consolidate.
- **`markets.push_tokens`** has 2 ALL-cmd policies with identical
  `auth.uid() = user_id` predicates. Same — consolidate.

## Methodology

For each of the 56 tables in `markets`:

1. Confirmed RLS is enabled (`pg_class.relrowsecurity`).
2. Listed every policy via `pg_policy` with command, role, USING
   clause, WITH CHECK clause.
3. Categorized each policy as: user-scoped (good), public-read
   (intentional for reference data), service-role-only (intentional
   for worker write paths), or anomalous.
4. Verified anomalous expressions against actual schema.

## Detailed flags

### Flag #1 — `ai_briefs` insert allows any caller to claim any owner_user_id

```sql
-- Current
CREATE POLICY "service role inserts briefs" ON markets.ai_briefs
  FOR INSERT TO public
  WITH CHECK (true);
```

Any authenticated user can `INSERT INTO markets.ai_briefs (owner_user_id, …)
VALUES ('<some-other-user-uuid>', …)`. SELECT correctly scopes by
`owner_user_id = auth.uid()`, so the inserted row is invisible to the
attacker — but visible to the *victim* if they hit a brief view, and
visible to admins / ops queries that don't filter by owner. Pollution
risk, not leak risk.

**Fix:** restrict to service role OR enforce `owner_user_id = auth.uid()`:

```sql
DROP POLICY "service role inserts briefs" ON markets.ai_briefs;
CREATE POLICY "ai_briefs_service_insert" ON markets.ai_briefs
  FOR INSERT TO public
  WITH CHECK (auth.role() = 'service_role');
```

**Severity for closed beta:** low — friends/family wouldn't exploit.
**Severity for public launch:** medium — fix before.

### Flag #2 — `signals_macro_context` insert has same WITH CHECK true

```sql
CREATE POLICY "service insert macro context" ON markets.signals_macro_context
  FOR INSERT TO public
  WITH CHECK (true);
```

Same pattern, same fix. Apply the same role-restricted version.

### Flag #3 — `signals_macro_context` SELECT references non-existent column

```sql
CREATE POLICY "tenant read macro context" ON markets.signals_macro_context
  FOR SELECT TO public
  USING (
    tenant_id = (SELECT tenant_id FROM auth.users WHERE users.id = auth.uid())
    OR tenant_id IS NULL
  );
```

`auth.users.tenant_id` does not exist on the prod schema. Verified via
`information_schema.columns`. The first branch of the OR raises
a runtime error when evaluated — Postgres will likely short-circuit to
returning rows matching only `tenant_id IS NULL`, but the policy's
intent (tenant scoping) is broken.

**Fix:** either add a `tenant_id` column to `auth.users` via JWT claim
or app metadata, OR rewrite the policy to reference a join table that
maps `user_id → tenant_id` (likely `public.user_roles` since
`platform_enforce_tenant_franchise_hierarchy` migration adds the
relevant constraints).

**Severity for closed beta:** low — single-tenant beta means
`tenant_id IS NULL` selects work fine.
**Severity for public launch:** medium — multi-tenant signal-context
isolation is broken.

### Flag #4 — `holdings` has duplicate policy set

8 policies, 4 redundant pairs. Both predicate identically:

```sql
holdings_owner_select   -- TO authenticated, USING (owner_user_id = (SELECT auth.uid()))
holdings_select_own     -- TO public,        USING (owner_user_id = auth.uid())

holdings_owner_insert   -- TO authenticated, WITH CHECK (owner_user_id = (SELECT auth.uid()))
holdings_insert_own     -- TO public,        WITH CHECK (owner_user_id = auth.uid())

… and same for update/delete.
```

The two sets were added in different migrations (one targeting public
role, one targeting authenticated role). They evaluate identically but
double policy evaluation per query is wasted CPU and a future
maintenance trap (a fix to one set won't update the other).

**Fix:** drop the `_owner_*` set OR the `_own` set in a follow-up
migration. Pick one convention and stick to it project-wide.

**Severity:** cosmetic. No security impact.

### Flag #5 — `push_tokens` has 2 redundant ALL policies

```sql
"Users manage own push tokens" -- TO authenticated, USING (auth.uid() = user_id) WITH CHECK (auth.uid() = user_id)
"users own push tokens"        -- TO public,        USING (user_id = auth.uid())
```

Same redundancy as holdings. Same fix recommendation.

## Recommendations

### For closed-beta launch (now)

No changes required. The three flagged data-pollution risks are
unlikely to be exploited by 10–20 hand-picked friends/family users.

### For public launch (before April 1 2027)

1. Fix flag #1 and flag #2 — replace `WITH CHECK true` with
   `auth.role() = 'service_role'` on `ai_briefs` and
   `signals_macro_context` INSERT policies.
2. Fix flag #3 — rewrite `signals_macro_context` SELECT policy to use
   a real tenant-resolution path.
3. Consolidate flag #4 + #5 — pick a single policy-naming convention
   and drop the duplicates.
4. Audit functions and views in the `markets` schema for
   `SECURITY DEFINER` settings that may bypass RLS. (Not in this
   audit's scope.)
5. Consider enabling `FORCE ROW LEVEL SECURITY` on all user-data
   tables. Currently `relforcerowsecurity = false` everywhere; the
   worker uses the service-role JWT to bypass RLS for legitimate
   cross-user reads. If any future code path runs as table owner, RLS
   would silently be off. Forcing RLS removes that risk.

## Verification queries used

```sql
-- RLS state across markets.*
SELECT n.nspname, c.relname, c.relrowsecurity, c.relforcerowsecurity,
       (SELECT count(*) FROM pg_policy p WHERE p.polrelid = c.oid) AS policy_count
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'markets' AND c.relkind = 'r'
ORDER BY n.nspname, c.relname;

-- Policy detail per table
SELECT c.relname, p.polname,
       CASE p.polcmd WHEN 'r' THEN 'SELECT' WHEN 'a' THEN 'INSERT'
                     WHEN 'w' THEN 'UPDATE' WHEN 'd' THEN 'DELETE'
                     WHEN '*' THEN 'ALL' END AS cmd,
       array_to_string(ARRAY(SELECT rolname FROM pg_roles WHERE oid = ANY(p.polroles)), ',') AS roles,
       pg_get_expr(p.polqual,      p.polrelid) AS using_expr,
       pg_get_expr(p.polwithcheck, p.polrelid) AS with_check_expr
FROM pg_policy p
JOIN pg_class c ON c.oid = p.polrelid
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'markets'
ORDER BY c.relname, p.polname;

-- Verify suspect column reference
SELECT column_name FROM information_schema.columns
WHERE table_schema='auth' AND table_name='users' AND column_name='tenant_id';
-- Returns 0 rows → auth.users.tenant_id does not exist.
```
