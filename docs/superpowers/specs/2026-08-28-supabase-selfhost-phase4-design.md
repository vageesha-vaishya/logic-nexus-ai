# Self-Hosted Supabase Migration — Phase 4: Edge Function Deployment - Design Specification

## 1. Background

Phase 1 (complete) stood up self-hosted's Edge Runtime container (`supabase/edge-runtime:v1.74.0`), already configured in `docker-compose.yml` to run in `--main-service /home/deno/functions/main` mode — but no `main` function exists yet, and `deploy/selfhosted-supabase/volumes/functions/` (the bind-mount source) is empty. Phase 1's README explicitly documents this as a known limitation: "this only proves the Edge Runtime container starts and its healthcheck TCP port responds. None of the platform's real Edge Functions are deployed yet."

Production (Supabase Cloud, project `gzhxgoigflftharcmdqj`) currently has **135 ACTIVE Edge Functions** (confirmed via `mcp__claude_ai_Supabase__list_edge_functions`). Source code for all of them — plus some additional unused/deprecated directories, 155 total — already exists in the repo at `supabase/functions/`, each as its own directory with an `index.ts`, following the standard Supabase CLI project layout, with per-function settings (`verify_jwt`) in `supabase/config.toml`.

This phase deploys that source to self-hosted's Edge Runtime, in secret-availability-ordered batches (per user decision during brainstorming — see §2).

## 2. Goals / Non-Goals

**Goals:**
- Author a `main` router function (`supabase/functions/main/index.ts`) that self-hosted's Edge Runtime dispatches all `/functions/v1/*` traffic through, matching the `--main-service` mode already configured in Phase 1's `docker-compose.yml`. This is Supabase's standard, documented pattern for self-hosted multi-function deployment — not a bespoke design.
- Classify all 135 production-deployed functions by their actual runtime dependencies: which need only the standard `SUPABASE_URL`/`SUPABASE_ANON_KEY`/`SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_DB_URL` (already provisioned in Phase 1's `functions` service) versus which need one or more of the ~60 distinct third-party secrets found across the codebase (LLM provider keys, OAuth client secrets, payment/email/messaging provider keys, etc.) — tracing actual imports, including transitively through `supabase/functions/_shared/*.ts`, not just each function's own file.
- Deploy in batches ordered by secret availability: **Batch 1** covers the router plus every function needing only standard `SUPABASE_*` vars. Later batches, one per logical secret-group (e.g. "LLM providers," "OAuth providers," "payment/messaging"), proceed only once the user has supplied real values for that group's secrets via the repo-root gitignored `env` file (this project's established secrets convention).
- Resolve the JWT-verification architecture gap (see §3) so self-hosted's actual per-function auth enforcement matches production's, not just "some single global setting that happens to work for the functions tested so far."
- Per-batch verification: every function deployed in a batch is invocable through self-hosted's real Kong-routed `/functions/v1/<name>` URL and returns a sane response (correct routing + correct auth behavior) — not full business-logic correctness testing of all 135, which is out of scope.

**Non-Goals:**
- Full business-logic testing of all 135 functions' actual behavior (e.g., confirming `calculate-quote-financials` produces mathematically correct output) — this phase proves *deployment and routing* work, matching Phase 1's own "proves the container responds" standard for infra work. Functional regression testing against self-hosted is a cutover-adjacent (Phase 6) concern.
- Obtaining actual secret values on the user's behalf — Supabase Edge Function secrets are write-only and cannot be read back from production via any API; this phase can only classify *which* secrets each function needs, not supply their values.
- Migrating or changing which functions exist — this phase deploys exactly what's live on production today (135 functions), not a refactor or cleanup of the 20 additional unused/deprecated local directories (those are explicitly out of scope; deploying dead code some maintainer already decided not to keep on production would be scope creep).
- Any change to production. Every production interaction in this phase is a read (function list, function metadata) — nothing is deployed to or altered on production.

## 3. Architecture

**3a. The router function.** Self-hosted's Edge Runtime, configured with `command: ["start", "--main-service", "/home/deno/functions/main"]`, invokes exactly one entry point for every request under `/functions/v1/*`. `supabase/functions/main/index.ts` must: parse the request path to extract the target function name (the segment after `/functions/v1/`), dynamically import that function's own handler module from its sibling directory (`../<function-name>/index.ts`), and delegate the request to it. This is the standard, Supabase-documented self-hosted pattern (referenced in Supabase's own reference self-hosting `docker-compose.yml`, which this project's Phase 1 compose file was adapted from) — not a novel design this project is inventing.

**3b. The JWT-verification gap.** Production enforces JWT verification per-function: `supabase/config.toml` explicitly sets `verify_jwt = false` for 85 functions; every function not listed defaults to Supabase's platform default (`verify_jwt = true`), enforced by the platform gateway *before* the function's own code ever runs. Self-hosted's Edge Runtime, running everything through one `main-service`, only exposes a single global `VERIFY_JWT` env var — there is no per-route gateway-level enforcement available to a main-service deployment. Setting it `true` would reject the 85 functions that need to be reachable without a platform-verified JWT (e.g. public webhooks, or functions doing custom auth). Setting it `false` makes every function reachable with no JWT verification at all, silently changing the security posture for however many of the remaining ~50 functions don't *also* perform their own internal auth check (several already do, via `supabase/functions/_shared/auth.ts`'s `requireAuth()`, since defense-in-depth against a misconfigured gateway is reasonable practice — but this must be confirmed per-function, not assumed).

**Resolution:** set self-hosted's global `VERIFY_JWT=false` (the permissive setting, required for the 85 explicit no-verify functions to work at all), and have the **router itself** perform JWT verification for every function *not* explicitly listed as `verify_jwt = false` in `config.toml` — i.e., the router reconstructs production's actual enforcement matrix from the same source of truth (`config.toml`) that production's platform reads, rather than relying on a blanket toggle. Before dispatching to a function's handler, the router checks a generated list (function name → verify_jwt bool, derived directly from `config.toml`) and, for any function requiring it, validates the request's `Authorization: Bearer <jwt>` against self-hosted's own JWT secret before invoking the handler — mirroring what the platform gateway does for production, just implemented in the router instead of unavailable infrastructure. Functions with their own additional internal auth checks (e.g. `requireAuth()`) are unaffected either way; this only closes the gap for functions that were implicitly relying on the platform's default enforcement without checking auth themselves.

**3c. Deployment mechanism.** Function source is bind-mounted the same way Phase 1's other config files are (`kong.yml`, `volumes/db/*.sql`) — meaning it hits the identical, already-documented "bind-mounts don't refresh from git on redeploy" gotcha (README §"Operational gotcha"). Each batch's rollout requires: commit the batch's function directories (plus any `main`/router changes) to the repo, `scp` them to the live bind-mount path on the VPS, restart the `functions` container. No new deployment mechanism needs inventing; this reuses Phase 1's established procedure.

**3d. Secret provisioning.** Third-party secrets follow this project's established convention: real values go in the repo-root gitignored `env` file (never in a report file, never printed in any committed artifact), then get provisioned into the self-hosted stack's actual runtime `.env` (the same Coolify-managed `.env` at `/data/coolify/applications/i64jlyerora7ao9vkw5sweh3/.env` that already supplies `JWT_SECRET`/`SERVICE_ROLE_KEY`/etc. to the `functions` service via `docker-compose.yml`'s `${VAR}` substitution) as each secret-dependent batch is ready to deploy.

## 4. Safety & Monitoring

- **Zero production traffic, still.** This phase doesn't change that Phase 1 established — self-hosted continues serving no live app traffic. A misconfigured function or router bug has no user-facing blast radius before Phase 6.
- **Read-only against production** — every production interaction (function listing, function metadata, `config.toml`'s already-repo-local content) is a read; nothing is deployed to or altered on production itself.
- **Health checks**: the same 4 standard production health-check curls after every batch's container restart, per established practice — a `functions` container restart is a state-changing step on shared infrastructure (same VPS as 24 unrelated apps) even though this specific container's own traffic is currently zero.
- **No interaction with Phase 2's replication subscription or Phase 3's storage sync** — this phase touches only the `functions` container and its bind-mounted source; no schema, table, bucket, or policy changes.
- **Secrets discipline**: no third-party secret value is ever committed to git, printed in an SDD report file, or logged — matching this project's established convention throughout Phases 1-3.

## 5. Verification Plan

1. **Router correctness**: for a small sample of already-deployed (Batch 1) functions, invoke each through self-hosted's real Kong-routed URL (`https://supabase.sosservices.online/functions/v1/<name>`) and confirm the request actually reaches that function's own code (not a 404, not silently routed to the wrong function) — e.g. by checking for a distinctive response only that function would produce.
2. **JWT enforcement matches production's matrix**: for at least one `verify_jwt=false` function, confirm it's callable WITHOUT an `Authorization` header. For at least one function relying on the implicit `verify_jwt=true` default, confirm it's REJECTED without a valid JWT and SUCCEEDS with one.
3. **Per-batch secret-classification accuracy**: for each function claimed as "secret-free," grep confirms zero non-`SUPABASE_*` `Deno.env.get()` calls in its own file AND everything it imports from `_shared/`, not just its own file (avoiding the exact transitive-dependency miss that would silently misclassify a function).
4. **Health checks**: all 4 standard endpoints return 200 after every batch's container restart.
5. **No regression to already-deployed batches**: after each new batch's container restart, re-verify a sample of the PREVIOUS batch's functions are still reachable and correctly routed (a router bug introduced by a later batch could silently break earlier ones, since they all share the same router).

## 6. Open Items

- **Exact batch grouping and count** is deliberately left for the implementation plan to determine from the actual secret-classification data (§2's Goals), not guessed here — the natural groups (LLM providers, OAuth providers, payment/messaging/email providers, "everything else needing some other single secret") should emerge from the real classification pass, not be predicted in advance.
- **The ~20 unused/deprecated local function directories** (155 local minus 135 production-active) should be identified explicitly (by diffing the local directory list against production's active list) and excluded from every batch — deploying them would be silent scope creep, matching this spec's Non-Goals.
- **Router performance/cold-start behavior** at 135 functions' worth of dynamic-import branching is untested — if this becomes a real latency concern under actual load, it's a Phase 6/production-readiness question, not a Phase 4 blocker (self-hosted serves zero production traffic throughout this phase).
