# Self-Hosted Supabase Migration — Phase 5b: JWKS-Based Verification of Production Tokens - Design Specification

**Date:** 2026-08-31
**Scope:** Phase 5's JWT alignment (`docs/superpowers/specs/2026-08-31-supabase-selfhost-phase5-auth-migration-design.md`) aligned self-hosted's legacy HS256 `JWT_SECRET` with production's, on the assumption production's real signing secret was that same legacy HS256 secret. A real production access token supplied for verification during that phase's final review disproved this: production issues **ES256** tokens (asymmetric, via Supabase's JWT Signing Keys / JWKS feature), confirmed against production's live JWKS endpoint and empirically confirmed self-hosted rejects such a token outright (`"signing method ES256 is invalid"`). This phase makes self-hosted able to verify production's real, current tokens, while still being able to issue its own tokens for logins/signups that happen directly against it.

**Status:** Approved for implementation

## 1. Background

**What Phase 5 actually achieved vs. what it was meant to achieve:** all of Phase 5's mechanics (updating `JWT_SECRET` in Coolify's env store and the `db` GUC, regenerating `ANON_KEY`/`SERVICE_ROLE_KEY` to match, recreating the affected containers) were executed correctly against their target — the legacy HS256 secret. The stated goal ("a still-valid production access token keeps validating against self-hosted immediately after cutover") is not met for any token issued under production's current scheme, because HS256 (symmetric, shared-secret) and ES256 (asymmetric, public/private keypair) are not interchangeable — no shared value can make an HS256-only verifier accept an ES256-signed token. This was proven empirically, not inferred: a real, current production access token (`alg: ES256`, `kid: c3dfc32a-6c1a-49b1-8830-4f554903ff30`) returned `403 {"code":"bad_jwt","msg":"...signing method ES256 is invalid"}` from self-hosted's `/auth/v1/user`.

**Confirmed via production's live JWKS endpoint** (`https://gzhxgoigflftharcmdqj.supabase.co/auth/v1/.well-known/jwks.json`): it currently publishes 2 ES256 public keys (`kid`s `c3dfc32a-6c1a-49b1-8830-4f554903ff30` and `5a9b1446-5e00-4a18-a807-fc54aba5241c`) — the first matches the sampled token exactly; the second is presumably a standby/rotation key. The legacy HS256 secret retrieved from the dashboard for Phase 5 still exists and is exposed there, but is not what's actively signing current tokens.

**Researched and confirmed (not assumed) before this design was written**, against GoTrue v2.195.0's actual source (`supabase/auth`, `internal/conf/jwk.go`) and PostgREST's documented config:
- `GOTRUE_JWT_KEYS` accepts a JSON array of JWKs. Verify-only entries can be bare public keys (no private/`d` component) — this is exactly production's JWKS shape, usable as-is. Exactly one entry in the whole array must be marked `key_ops: ["sign"]` (with its private component present) — GoTrue uses that one to sign new tokens it issues itself; `Validate()` errors if zero or more than one entry claims the signing role.
- Setting `GOTRUE_JWT_KEYS` at all switches GoTrue's own token issuance off `GOTRUE_JWT_SECRET` entirely, onto the one designated signing key in that array.
- `PGRST_JWT_SECRET` (PostgREST) directly accepts a literal JWK or a full `{"keys":[...]}` JWKS JSON blob — no separate config path needed, and no private key material required since PostgREST never signs, only verifies.
- Neither GoTrue nor PostgREST support fetching a JWKS from a live URL — key material is static, supplied via env var. If production rotates its ES256 keys after this phase's snapshot is taken, self-hosted's copy goes stale until manually re-synced. Acceptable here because this is meant to be a short cutover-window measure, not a permanent architecture, but the whole reason this matters at all *this time* was a real, undocumented mismatch — a full re-check of production's JWKS immediately before the actual cutover is worth budgeting for, not assumed away.
- This exact scenario — a self-hosted stack that needs to verify (not just issue) another, external Supabase Cloud project's tokens during a migration window — is not a documented Supabase self-host pattern. This phase assembles it from GoTrue/PostgREST's individual, real capabilities above, not from an official recipe.

## 1a. Audit pass (2026-08-31) — verified against GoTrue's actual source and this repo's live config

The §1 research above came from a summary. This pass re-verified the load-bearing claims directly and found four things that change the design.

**Finding 1 — the proposed new ES256 signing key would break self-hosted's own `ANON_KEY`/`SERVICE_ROLE_KEY`, and there is a simpler path that avoids the problem entirely.**

Read directly: `internal/api/auth.go`'s `parseJWTClaims` builds its parser as `jwt.NewParser(jwt.WithValidMethods(config.JWT.ValidMethods))`, and its keyfunc has an explicit HS256 backward-compat fallback — if a token carries no `kid` (or the `kid` isn't found) and `alg == HS256`, it verifies against `config.JWT.Secret`. That fallback is exactly what keeps Phase 5's bare, `kid`-less HS256 `ANON_KEY`/`SERVICE_ROLE_KEY` working today.

But `internal/conf/configuration.go`'s `ApplyDefaults` shows two decisive details: (a) when `JWT_KEYS` is non-empty, the legacy `JWT.Secret` is **not** added to `Keys`; and (b) `ValidMethods` is derived *solely* from the algorithms of the keys in `Keys`. Since golang-jwt's parser rejects a token whose `alg` isn't in `ValidMethods` **before** the keyfunc ever runs, an all-ES256 key list yields `ValidMethods = ["ES256"]` and makes that HS256 fallback dead code. §3's step 1 as originally written would therefore break self-hosted's own anon/service keys — precisely the self-inflicted breakage Phase 5 already suffered once and had to fix mid-flight.

§3's step 5 (regenerate both keys under the new signing key) does anticipate this, so the spec is not *wrong* — but there's a materially simpler and lower-risk option it missed: **keep self-hosted's existing HS256 secret as the signing key**, expressed as an `oct` JWK with `key_ops: ["sign"]`, alongside production's two ES256 public keys as verify-only entries. Then `ValidMethods = ["HS256", "ES256"]`, self-hosted's own token issuance behaviour is completely unchanged, and `ANON_KEY`/`SERVICE_ROLE_KEY` **need no regeneration at all** — they keep verifying through the same fallback path they use today. Upstream's own test fixture (`internal/conf/jwk_test.go`, `testJwtKey`) confirms mixed arrays are supported, containing `oct`/HS256, `RSA`/RS256, `EC`/ES256 and `OKP`/EdDSA entries side by side. **This removes the riskiest step in the plan** and is the approach §3 has been rewritten to take.

**Finding 2 — PostgREST needs no compose-file change; the wiring already exists.** `docker-compose.yml:174` already reads `PGRST_JWT_SECRET: ${JWT_JWKS:-${JWT_SECRET}}`, and `JWT_JWKS` is already a registered (currently empty) key in the live `.env`. Setting its value is sufficient — no new variable, no compose edit, no deploy-branch sync for this half.

**Finding 3 — GoTrue's half *does* require a compose-file change, which drags in Phase 5a's deploy-branch constraint.** There is no `GOTRUE_JWT_KEYS` line anywhere in `docker-compose.yml` (only `GOTRUE_JWT_SECRET`, line 129). Adding one is a structural compose change, so per Phase 5a's live-verified finding it must land on the `deploy/supabase-selfhost-phase1` branch Coolify actually deploys from — not just `main` — or the next real redeploy silently reverts it. Registering the var's *value* in Coolify's env store is not sufficient on its own here, unlike Finding 2's case.

**Finding 4 — the `functions` service was missed entirely by §2's non-goals, and it matters more than the services that were listed.** The edge-function router at `supabase/functions/main/index.ts` performs its own JWT signature verification, hardcoded to HMAC: `crypto.subtle.verify("HMAC", key, signature, signedData)` (line 294), with the key imported from the shared `JWT_SECRET`. There is no algorithm branching — a production ES256 token will fail signature verification there exactly as it did at `auth`/`rest`, for all 109 deployed functions gated by this router. §2's non-goals named `storage` and `realtime` but never `functions`, which is the larger exposure of the three. Now explicitly addressed in §2.

## 2. Goals / Non-Goals

**Goals:**
- Self-hosted's `auth`/`rest` (and any other JWT-verifying service) accept currently-valid production-issued ES256 access tokens — verified against the real, still-valid token sampled during Phase 5's review, not merely against a freshly-minted test token.
- Self-hosted continues to be able to issue its own valid tokens for logins/signups happening directly against it (both before and after the eventual cutover) — via a newly-generated, self-hosted-owned signing keypair.
- **`ANON_KEY`/`SERVICE_ROLE_KEY` are left completely untouched** — per §1a Finding 1, keeping self-hosted's HS256 secret as the designated signing key means `ValidMethods` still includes HS256 and both keys keep verifying through GoTrue's existing `kid`-less fallback. Not regenerating them is a deliberate goal of this design, not an omission: Phase 5 broke the stack precisely by changing these, and the safest version of this phase doesn't touch them at all.
- Zero change to production Supabase Cloud (this phase only ever reads production's already-public JWKS endpoint).

**Non-Goals:**
- Live/automatic JWKS refresh from production — explicitly out of scope per the researched limitation above; a manual re-check immediately before the real cutover is a process step, not something this phase automates.
- Migrating `auth.sessions`/`auth.refresh_tokens` — unchanged from Phase 5's own non-goal; still no silent-refresh continuity across cutover, only access-token verification continuity for whatever's still unexpired.
- Any change to how production issues or rotates its own keys.
- **`storage` and `realtime`'s own independent JWT verification** (`AUTH_JWT_SECRET`/`API_JWT_SECRET`, both currently the legacy HS256 secret, per `docker-compose.yml`) are **not** covered by this design — research for this phase focused on `auth`/`rest` specifically, and whether `storage-api`/`realtime` support an equivalent JWKS-shaped secret was not checked. This is a real, acknowledged scope gap, not an oversight glossed over: a production-issued token presented directly to self-hosted's `storage` or `realtime` endpoints will very likely still fail the same way `rest` did before this phase, unless a follow-up confirms and applies the same treatment there.
- **The `functions` router's own JWT verification is likewise out of scope, and is the largest of these three gaps** (added after §1a Finding 4 — the original draft of this spec omitted it entirely). `supabase/functions/main/index.ts` verifies signatures with hardcoded HMAC (`crypto.subtle.verify("HMAC", ...)`) against the shared `JWT_SECRET`, with no algorithm branching, so production ES256 tokens will be rejected for all 109 deployed edge functions gated by that router. Unlike `auth`/`rest`, this is **our own code**, not a third-party service's config — fixing it means teaching the router to verify ES256 against production's JWKS, which is a genuine (if small) code change rather than an env-var change, and deserves its own scoped piece of work rather than being smuggled into this phase. Explicitly deferred, explicitly flagged: any client calling self-hosted edge functions with a production-issued token will still fail after this phase completes.

## 3. Approach

**Rewritten after §1a's audit.** The original draft proposed generating a new ES256 signing key and regenerating `ANON_KEY`/`SERVICE_ROLE_KEY` under it; Finding 1 showed that path needlessly breaks and then re-fixes the stack's own anon/service keys. The approach below keeps the existing HS256 secret as the signing key, which leaves those keys untouched and working.

1. **Re-fetch production's JWKS** — `GET https://gzhxgoigflftharcmdqj.supabase.co/auth/v1/.well-known/jwks.json`, re-confirming the 2 keys recorded in §1 or capturing whatever has changed since. Never reuse this design's snapshot.
2. **Express self-hosted's existing HS256 secret as an `oct` JWK** with a stable, self-hosted-specific `kid`, `alg: "HS256"`, `key_ops: ["sign"]`, and `k` set to the base64url encoding of the current `JWT_SECRET`. This is the one and only signing key (GoTrue's `Validate()` errors on zero or multiple). Self-hosted's own token issuance behaviour is unchanged from today's.
3. **Assemble the key array**: that one `oct` signing key + production's ES256 public keys verbatim (already `key_ops: ["verify"]`, already public-only — no transformation needed). This yields `ValidMethods = ["HS256", "ES256"]`, so both self-hosted's own tokens and production's are accepted.
4. **Add `GOTRUE_JWT_KEYS` to the `auth` service in `docker-compose.yml`** and — per §1a Finding 3 — land that compose change on **both** `main` and `deploy/supabase-selfhost-phase1`, the same two-branch shape Phase 5a established, or the next real redeploy reverts it. Leave `GOTRUE_JWT_SECRET` in place: it stays load-bearing here, since the `kid`-less HS256 fallback in `parseJWTClaims` reads it directly, which is what keeps `ANON_KEY`/`SERVICE_ROLE_KEY` working.
5. **Set `JWT_JWKS`** (already wired to `PGRST_JWT_SECRET` at `docker-compose.yml:174`, already a registered empty key in the live `.env` — §1a Finding 2) to a `{"keys":[...]}` JWKS containing the same set, with the signing key's `oct` entry included so PostgREST also accepts self-hosted-issued tokens. **No compose change for this half**, so no branch-sync needed for it.
6. **Register both values in Coolify's env store** (`PATCH .../envs`, both the production and `is_preview` copies, per the pattern confirmed during Phase 5) **and** update the on-disk `.env`, then recreate only `auth` and `rest`. Never `db`. Expect the same `env_file`-wide collateral-recreate behaviour Phase 5 documented — verify actual post-recreate container timestamps rather than assuming the named-services list is the real blast radius.
7. Verify (see §4).

## 4. Verification Plan

1. **The real, already-sampled production token** (the one that returned `403` before this phase) — re-test it against self-hosted's `/auth/v1/user` after this phase's changes. Expected: `200`, correct user data. This is the actual goal, proven against real evidence, not a fresh synthetic token.
2. Confirm self-hosted's own token issuance still works: create a test signup via GoTrue's Admin API (same substitute Phase 5 established, given the still-open SMTP gap), obtain a password-grant token, confirm it validates (`/auth/v1/user` → `200`). Decode its header and record whether it now carries the signing key's `kid` — GoTrue may start stamping one once `JWT_KEYS` is configured, which is expected and harmless, but should be observed rather than assumed either way.
3. Confirm the **untouched** `ANON_KEY`/`SERVICE_ROLE_KEY` still work — this is the specific regression §1a Finding 1 exists to prevent, and the single most likely way this phase breaks the stack. `GET /rest/v1/...` with the existing `ANON_KEY` → `200`, not `401 PGRST301`. Test this against **both** `rest` and `auth` (e.g. an `/auth/v1/admin/users` call with `SERVICE_ROLE_KEY`), since the two services resolve keys by different mechanisms — PostgREST from the `JWT_JWKS` blob, GoTrue from its `kid`-less HS256 fallback — and one working does not imply the other does.
4. Confirm the 4 standard production health-check curls stay `200` throughout.
5. Confirm none of the 103 real migrated users' own data was touched (row counts unchanged) — this phase only changes verification/signing configuration, never touches `auth.users`/`auth.identities` data.
6. Re-verify production's JWKS one more time at the end of implementation (not just at the start) — if it changed mid-implementation, the config assembled in step 3-4 above would already be stale; catch this before declaring the phase done, don't assume the snapshot from step 2 held for the whole implementation window.

## 5. Rollback

Rollback is materially cheaper under the revised approach than it would have been under the original draft, because no keys are regenerated and no token material changes: clear `GOTRUE_JWT_KEYS` and `JWT_JWKS` back to empty, and recreate `auth`/`rest`. GoTrue then falls back to `GOTRUE_JWT_SECRET` and PostgREST to `${JWT_JWKS:-${JWT_SECRET}}`'s default branch — both exactly as Phase 5 left them. `ANON_KEY`/`SERVICE_ROLE_KEY` are never touched in either direction, so there is nothing to restore for them.

The compose-file change from §3 step 4 can be left in place on rollback (an empty `GOTRUE_JWT_KEYS` is inert) — reverting the env-var values is sufficient and avoids a second two-branch compose change. Net effect: the stack returns to Phase 5's end state, working as it does today, minus the ability to verify production's real tokens — the gap this phase exists to close. No production-side rollback is needed or possible from this phase's side; nothing here writes to production.
