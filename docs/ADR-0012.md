# ADR-0012: Work Package Transactional Persistence and Registry-Governed Template Access

- Status: Accepted
- Date: 2026-03-24
- Decision Owners: AMRO Architecture, Platform API Team
- Scope: AMRO Work Packages Module (15.2A.2 high-priority closure)

## Context

The AMRO Work Packages module previously validated business rules in API code but did not guarantee durable writes in the same execution boundary. Template visibility decisions depended on local string rules, and transition transaction events were not persisted in an immutable audit trail. This introduced risk in concurrent transitions, cross-service consistency, and audit evidence quality.

## Decision

1. Persist create, transition, and clone-template operations through durable `amro_ops` write paths, returning success only after confirmed database commit.
2. Enforce optimistic locking on `public.work_packages` with a `version` column and `expected_version` transition precondition.
3. Replace hard-coded template visibility heuristics with registry-backed authorization checks via `TemplateRegistryClient`.
4. Cache registry responses with tenant/user-prefixed keys, max size 500, and 5-minute TTL.
5. Persist workflow transaction logs in immutable `amro_audit.amro_workflow_tx_log`.
6. Expose operational health and audit retrieval endpoints:
   - `GET /api/v2/amro/ops/health/persistence`
   - `GET /api/v2/amro/audits/workflow/{transitionId}`

## Consequences

- Positive:
  - Removes in-memory-only success paths for critical mutation operations.
  - Prevents lost updates in concurrent state transitions.
  - Aligns template access decisions with authoritative registry governance.
  - Improves compliance posture with immutable transition logs and masked payload persistence.
  - Adds explicit operational observability for persistence and workflow audit retrieval.
- Trade-offs:
  - Adds external dependency on template registry availability.
  - Introduces additional persistence and audit write overhead per transition.

## Alternatives Considered

- Keep in-memory policy validation and defer persistence to async workers: rejected due to commit ambiguity and audit drift.
- Continue hard-coded template checks: rejected due to governance drift and tenant/user authorization inconsistency.
- Store transition logs in mutable operational tables: rejected due to audit immutability requirements.
