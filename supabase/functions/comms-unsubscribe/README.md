# `comms-unsubscribe`

One-click unsubscribe handler per **RFC 8058**. Receives unsubscribe requests from email recipients (via the `List-Unsubscribe` header that send-paths add to outbound mail), verifies the HMAC-signed token, and inserts a `comms.suppressions` row.

Per [`docs/plans/2026-05-28-modules/comms-infrastructure.md §4.6`](../../../docs/plans/2026-05-28-modules/comms-infrastructure.md). Closes **G-CR-3** (no suppression list, no unsubscribe enforcement).

## Three request shapes handled

| Method | Trigger | Response |
|---|---|---|
| `GET ?token=...` | Recipient clicks the `List-Unsubscribe` URL in their mail UI | HTML confirmation page with a single "Unsubscribe" button |
| `POST ?token=...` body `List-Unsubscribe=One-Click` | **RFC 8058 one-click** — Gmail/Yahoo/Apple fires this directly when user hits "Unsubscribe" inside the mail client | `200 OK` plain text — mail client doesn't render the body |
| `POST ?token=...` form-submit | User confirmed via the GET landing page | HTML success page |

## Token

Generated by send-paths via `_shared/comms-unsubscribe-token.ts`. HMAC-SHA256-signed, stateless, 90-day default TTL.

Format: `<payload_b64url>.<signature_b64url>` where payload is JSON `{tenant_id, address, channel_kind, exp, nonce}`.

## Configuration

| Variable | Source |
|---|---|
| `COMMS_UNSUBSCRIBE_HMAC_SECRET` | Generate a 32+ char random secret. Store in Supabase project edge-function secrets. **Will migrate to `core.secrets` (purpose='hmac_unsubscribe') in a follow-up.** |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Auto-injected by Supabase edge runtime |

## URL to register

The send-path helpers (`buildListUnsubscribeHeaders`) construct URLs like:

```
https://<project-ref>.supabase.co/functions/v1/comms-unsubscribe?token=<token>
```

This needs to be the same URL the function is deployed at; the helpers take the base URL as a parameter so dev/prod environments work.

## Effect

On successful unsubscribe:
- Inserts row into `comms.suppressions` with `reason='unsubscribe'`, `added_by_kind='recipient_unsubscribe'`.
- `source_metadata` captures user-agent, IP, one-click flag, original token nonce + expiry for audit.
- Idempotent: clicking the link twice does nothing on the second click (UNIQUE constraint + `ignoreDuplicates: true`).

After unsubscribe, every subsequent call to `comms.is_suppressed()` for this (tenant, channel, address) returns true. Send paths consult this before delivery.

## What this does NOT do

- **Does not unsubscribe from transactional mail** (password resets, security alerts, OTP). These have separate send paths that intentionally skip the suppression check because they are required for account operation. See `comms-infrastructure.md §6` for the policy.
- **Does not delete the user's account** — that's a separate flow gated by tenant admin and requires identity verification.

## Testing

```bash
# 1. Generate a token via the shared helper (in a dev script)
# 2. GET https://<project>/functions/v1/comms-unsubscribe?token=<token>
#    → HTML confirmation page
# 3. POST same URL with body "List-Unsubscribe=One-Click"
#    → 200 OK + a row in comms.suppressions
# 4. Verify comms.is_suppressed() returns true for the now-suppressed address
```
